## 0. Executive summary

Hutch already has more brand infrastructure than its public surface suggests: a DTCG-style token
source (`website/tokens.json`) that generates two checked-in stylesheets, a dark emerald identity
applied consistently to the marketing page and both dashboard shells, self-hosted Geist fonts with
OFL licence files, and one-off social cards. What it does **not** have is an identity system around
that foundation: the mark exists only as duplicated inline SVG (six occurrences across three HTML
roots), there is no logo master file, no PWA manifest or maskable icon, no raster favicon or
apple-touch-icon, no dark/tinted icon variants, no press kit, no brand-usage or trademark policy, and
no visual-regression or accessibility baseline for brand changes. Six existing brand/design
documents are relevant and were deliberately **not** read in this planning session (A.8, U01).

The critical ordering constraint is legal, not visual: **no logo, name, or tagline is generated
until the Phase 2 clearance protocol is documented and signed off** [COUNSEL]. Search and filing
decisions must be made before design investment (C02, C03, C04). The second constraint is
do-no-harm: Hutch ships as a local-first source checkout, so there is no server-side canary to a
user population; validation has to happen before merge (C11, C22).

The brief was written for a Next.js application. This repository is a Python/FastAPI + Jinja +
React-shell + Tauri + static-site product. Every declared input path was checked; the absent ones
are documented in A.9 and resolved to named equivalents rather than assumed. No file content was
invented for a missing path.

### R.1 Category identity systems - what works and why

The category's strongest identity systems share a small, repeatable stack: an explicit lockup
architecture, a single downloadable asset source, a retained signature colour, written naming rules,
and rights asserted separately from the code licence.

| System | What it does well | Source (retrieved 2026-10-28) |
|---|---|---|
| LM Studio | App-icon + wordmark lockup, "Lmmy" mascot, downloadable SVG/PNG pack, explicit misuse list, press contact | https://lmstudio.ai/brand |
| Open WebUI | Icon-first usage; horizontal lockup only when the name is needed; naming doctrine ("Open WebUI", never "OpenWebUI"); assets from one repo location; branding-protection clause in the licence for larger deployments (50+ users) | https://docs.openwebui.com/brand ; https://docs.openwebui.com/license |
| Home Assistant | Mark is a house + antenna; four layouts; "wordmark never without logomark"; dedicated 16x16 favicon/menu-bar variants; naming rules ("never HA/HASS"); logo trademark held by the Open Home Foundation, commercial use by permission | https://contributors.home-assistant.io/brand/name-and-logo/ ; https://raw.githubusercontent.com/home-assistant/assets/master/logo/README.md |
| Obsidian | Volcanic-rock mark; mark + wordmark colour rules; "do not edit, distort, recolor"; name/logo/app icon are trademarks; personal icon customisation allowed, commercial use by contact | https://obsidian.md/brand |
| n8n | October 2026 refresh of logo, typeface and colour while keeping the signature pink ("the pink stays"); community saw early versions; shipped across product, site, community and events; public design guidelines | https://blog.n8n.io/n8n-brand-refresh-2026/ ; https://guidelines.n8n.design/ |
| Ollama | Text-first, monochrome, install-command homepage; the product demo is the brand; MIT licence. No public brand/usage page was found, which is the category's common anti-pattern | https://ollama.com/ ; https://raw.githubusercontent.com/ollama/ollama/main/LICENSE |
| Jan | Category shortcut in the title tag ("Open-Source ChatGPT Replacement"); clear "your personal intelligence" line; download-proof statistic | https://www.jan.ai/ |
| Raycast | Keyboard-as-identity; short benefit phrase; reliability proof statistic | https://www.raycast.com/ |

Transferable patterns: (1) explicit lockup architecture with tiny-size variants; (2) one authoritative
asset source with a misuse list ("use provided files only"); (3) a signature colour that survives a
refresh; (4) naming rules written down and checkable; (5) brand rights asserted separately from the
MIT/source licence; (6) builder-first tone plus verifiable proof instead of superlatives.

Anti-patterns: no published asset/usage page (reproduction drift); identity louder than the task
(Domino's); rename with no migration plan (X).

**Trademark rights and AI.** US trademark rights arise from use in commerce; registration adds
nationwide rights (USPTO basics). USPTO AI practice guidance from 2024 applies the existing rules and

similar" material (US Copyright Office Part 3, pre-publication 2025-05-09), and vendors disclaim

**Token architecture.** The DTCG "Design Tokens Format Module 2025.10" is a Final Community Group
Report (2025-10-28), "considered stable" but explicitly not a W3C Standard and not on the Standards

since v4 but its docs warn that 2025.10 support is incomplete and "work in progress in v5"; current
release v5.7.1 (2026-10-24). Layered practice: raw value -> primitive -> simplified semantic alias ->
granular semantic -> component-specific.
Hutch already has most of this: `website/tokens.json` is DTCG-shaped (primitive -> semantic,
`$value`/`$type`, contrast `verify` pairs, and a `deprecated` migration ledger);

`tests/test_site_tokens.py` covers drift, shared-file equality and fallback-less `var()`
references. Three parallel namespaces still exist: site semantic `--color-*`, a Studio
`--hutch-*` namespace (with `--hutch-static-*`/`--hutch-alias-*`), and open-props, all mapped into
daisyUI roles; the `tokens.json` header claims a "component" tier that the file does not contain.

**Rollout and do-no-harm.** Feature toggles should be few and temporary, because each carries cost
(Fowler). SRE defines canarying as a partial, time-limited deployment plus evaluation. GrowthBook's

## Appendices

### Appendix A - Evidence and asset conventions

- Screenshots: docs/brand/evidence/phaseN/YYYY-MM-DD-surface-state-viewport.png. Each visual claim in a
  PR or doc links one file; no claim without a path (G3).
- Screenshot provenance recorded in the phase doc: route/URL, viewport, DPR, browser/revision, OS,
  font-loading wait, commit SHA, date.
- Asset provenance fields per exported file: source type (human-drawn, font-derived, AI-assisted with
  human redraw), tool and version if any, date, licence, approver, and the master file it came from.
- External sources: URL + retrieval date in the same row or paragraph; archived copy noted when the
  live page is bot-blocked.
- No emoji in docs, source or UI (repo policy). No banned words (G6).
