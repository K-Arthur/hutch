# OpenCode CLI coding handoff review

Reviewed 2026-10-09 for Hutch's Linux-first OpenCode coding-task handoff. This is documentation and public-issue research plus local contract inspection, not a live model call. The installed binary reports **opencode v2.0.24**; Hutch does not read its private auth file or make a paid request.

## Product fit and failure evidence

OpenCode's V2 CLI documents **mini** as its minimal interactive interface, **--prompt** for an initial prompt, and **--standalone** for a private server instead of a shared background service ([CLI](https://opencode.ai/v2/docs/cli)). Its agent configuration supports ordered allow/ask/deny rules and a positive **steps** limit; the final step removes tools and asks for a text summary ([agents](https://opencode.ai/v2/docs/agents), [permissions](https://opencode.ai/v2/docs/permissions)). The v2 provider documentation makes the OpenCode Go key flow distinct from reuse of the CLI's local sign-in. Hutch therefore labels them as two separate integrations: a provider connection for Hutch-managed calls, and an experimental local interactive coding handoff using the user's OpenCode CLI.

The interactive route is a deliberate fit for Hutch's current boundary. OpenCode's permission broker and API event transport are not Hutch-controlled. An OpenCode ACP user report describes a permission response being silently dropped after loading the same session under a different working directory, leaving the task hung ([issue #31964](https://github.com/anomalyco/opencode/issues/31964)). Hutch avoids resuming an external session or switching its project directory: each task gets a new CLI session in one isolated worktree, and the owner sees OpenCode's own terminal prompts.

Other public reports motivate explicit status and a step bound. A Cursor forum user reported Grok Bot's computer helper restarting when another message arrived during active work, leaving the task incomplete while consuming allowance; a product representative said the handoff could stop and restart the helper, and later identified minute-scale delays in browser actions ([report and staff response](https://forum.cursor.com/t/grok-bot-computer-use-agents-stall-and-fail-to-complete-simple-tasks/173037)). An OpenCode issue report describes repeated failed edits and missing loop detection, including that V2 agent steps are otherwise unbounded when unset ([issue #50073](https://github.com/anomalyco/opencode/issues/50073)). These are individual reports, not prevalence estimates. Hutch addresses their actionable part by saving the reviewed request, showing a durable handoff state, isolating each task from its source checkout, and setting OpenCode's supported step limit to 20. The limit is an OpenCode iteration ceiling, not Hutch usage accounting or a guarantee against wasted model calls.

A separate OpenCode report says project .opencode/plugins may load despite OPENCODE_DISABLE_PROJECT_CONFIG=1 and --pure ([issue #49836](https://github.com/anomalyco/opencode/issues/49836)). Until the installed version is proven to close that behavior, Hutch refuses a project worktree containing local plugin files. **--pure** and environment flags are defense in depth; they are not described as a sandbox.

## Hutch behavior and boundaries

1. A completed Hutch chat reply can seed a coding task. The owner sees the original request and the Bot's suggested brief, then edits and confirms the exact task.
2. The task must belong to a Bot whose workspace is explicitly configured to one existing Git folder. Hutch records its project identity and HEAD commit, then makes a new branch and worktree from that exact commit. Source-folder changes and untracked files are excluded; Hutch never copies the result back.
3. The command **hutch code run <id>** runs only in an interactive Linux terminal on the Hutch host. It starts the installed OpenCode mini interface with **--standalone**, **--prompt**, and a per-task agent config. No **--auto** option is used. A task is single-use; an interrupted checkout is retained for review rather than replayed.
4. The local OpenCode CLI uses its own sign-in, selected model, provider terms and usage pool. Hutch's connection records, admission limits and usage budgets do not cover OpenCode's model calls.
5. Hutch configures explicit tool-policy rules and asks OpenCode to prompt for shell commands, but does not broker those decisions. An approved shell command has the Linux user's filesystem, process and network authority; this feature is not protected by Hutch's bubblewrap shell sandbox. The owner must review each prompt and must not include passwords, tokens or other secrets in the brief.
6. OpenCode's output and edited files remain in its task worktree. Hutch records a bounded summary and file count, not a copy of the diff. Review the local branch before applying anything.

This is an experimental handoff, not an OpenCode runtime adapter, remote launcher, autonomous Cursor-style agent, private-session import, guaranteed hard spend cap, or verified sandbox. Pi remains unavailable. OpenCode permissions, providers, live CLI startup, task completion, account eligibility and paid usage have not been tested live. The e2e review uses a fake availability check and a local mock Hutch model; it never launches OpenCode.

## Follow-up gates

- Verify OpenCode v2.0.24 actually resolves the custom agent's ordered rules and 20-step cap in a no-network/no-model contract environment; the local debug config command timed out during inspection, so config loading remains a verification gap.
- Linux fake-CLI tests now launch the real `hutch code run` command, verify its reviewed prompt and isolated worktree, apply a fixture edit, send Ctrl+C to the foreground group, and check verified cleanup plus the persisted `stopped` result. A separate `hutch code reconcile` test records an owned process identity, verifies reconciliation leaves a live group untouched, then terminates it and confirms the task becomes `interrupted` and stays single-use. These tests use no OpenCode account, network access or model call. They cover state and process checks, not killing the actual Hutch controller mid-launch; no live OpenCode process was started.
- Recheck upstream plugin-loading issue against any supported OpenCode version before relaxing the plugin-directory refusal.
- Treat live account sign-in, provider usage, model selection, command permission UX, and OpenCode's resulting code quality as separate live checks requiring user-owned accounts and budget.
