# Grok Bot product and workflow review

Reviewed 2026-10-09 against the public [official Grok Bot documentation](https://docs.x.ai/grok-bot/overview), including Bot profiles, chat collaboration, Team Bots, computer access, approvals, routines, and troubleshooting. This is documentation research, not a live account trial or an independent verification of product behavior. User posts below are individual reports, not prevalence evidence.

## What fits Hutch

Grok Bot treats each Bot as a durable named teammate with its own role and conversation. Its guidance says a separate Bot is useful when the work has a distinct goal, sources/tools, style, approval boundary, or schedule; it recommends starting with one owner and adding specialists only for stable roles. The setup path is described as a message-led interaction. A Bot can suggest a focused long-lived Bot, but the owner is asked before creating several. This supports Hutch’s chat-first setup and the owner’s preference to keep a separate fleet page for larger rosters rather than make bot administration the default landing experience. The suggested threshold of roughly ten Bots is an owner heuristic, not a threshold established by Grok Bot research. ([Create and manage Bots](https://docs.x.ai/grok-bot/bots), [overview](https://docs.x.ai/grok-bot/overview))

Its chat surfaces task messages, tool activity, files, questions/forms, approvals, and drafts together. Users can send another message to redirect a running task or ask it to stop. Groups allow a small number of named Bots, explicit mentions, one shared outcome, and visible handoffs. Bots can also send asynchronous messages to one another, with the receiving Bot waking to continue. The docs warn that too many parallel handoffs can duplicate work and create noisy updates. These are useful patterns for Hutch’s named coordinator, direct user-to-task-Bot chats, and visible task/result cards. ([Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration))

Grok Bot’s task examples improve vague requests by stating the outcome, inputs or sources, constraints, output, and action boundary. The docs distinguish durable Bot description from task-specific chat instructions. For Hutch, this suggests a coordinator can turn an already-stated request into a better structured subtask rather than ask the user to repeat it. Preserve the original request and show the derived brief, inferred assumptions, selected context, owner, deliverable, and stop/approval boundary. Prompt wording must not grant tools, accounts, data, budgets, or permission. A one-off task brief must not silently modify a Bot’s standing instructions; creating a new persistent Bot or changing its role requires an explicit review and confirmation. ([Create and manage Bots](https://docs.x.ai/grok-bot/bots), [Use cases](https://docs.x.ai/grok-bot/use-cases), [Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration))

For work that benefits from multiple Bots, Grok Bot favors a shared outcome and explicit ownership per stage. Hutch should use the coordinator as the single parent for bounded work: select the smallest useful set of task Bots, assign one owner to each stage, route their questions and results back to the coordinator, and keep the user free to open a direct conversation with any task Bot. Approval cards, secret/login requests, and external message drafts should stay in an accountable one-to-one conversation; Grok Bot documents that these do not appear in its group chats. Hutch should never let a group feed or a broad mention stand in for action approval. ([Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration))

The product also gives a useful human-control pattern: pause at password, 2FA, CAPTCHA, payment, or site-required human steps; let the person take control in the live computer; continue from that session afterward. It explicitly warns against sending passwords or one-time codes in chat and says not to work around a challenge. Hutch already has a fixture-tested, experimental local Linux browser handoff in this area; its per-Bot profile isolation and secret redaction remain intentional differences. ([Use the computer and apps](https://docs.x.ai/grok-bot/computer-and-apps), [approvals and privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy))

## Boundaries Hutch should not copy

Grok Bot’s per-user Bots share one account-level computer, including browser sessions, files, and command-line credentials. Its docs distinguish Bot conversation context but explicitly say the computer and its sign-ins are shared; each Bot’s separate screen is not a security boundary. That makes handoffs convenient, but it means a login or file available to one Bot is available to the others. Hutch’s isolated per-Bot browser profiles, managed workspaces, per-run capability snapshots, and explicit artifact sharing provide a stricter boundary and should stay in place. Do not share a whole conversation or workspace just to delegate one task. ([overview](https://docs.x.ai/grok-bot/overview), [Use the computer and apps](https://docs.x.ai/grok-bot/computer-and-apps))

Grok Bot’s own security guide describes Auto Review as complementary to explicit controls and says it does not inspect every side effect. For Hutch, model-based review can help explain a risk but cannot replace exact action binding, capability enforcement, immutable receipts, compare-and-swap approvals, or process-level containment. Keep approval authority attached to the specific action and account/destination, with the review visible in the user’s chat. ([Approvals, security, and privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy))

Group conversation is not a universal control surface. Grok Bot documents that approval requests, login/secret requests, and email/Slack drafts stay out of group chats; bot-to-group handoff messages are text-only; and group notification controls differ from per-Bot notifications. Hutch should route private questions, human checkpoints, approvals, and rich artifact results to their owner/coordinator conversation, where they can be answered and audited. ([Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration), [settings and notifications](https://docs.x.ai/grok-bot/settings-and-notifications))

## Failure reports and operational lessons

The official troubleshooting guide treats a Bot as possibly waiting rather than simply broken: check the visible status, computer page, question, approval, login, CAPTCHA, or secret request; then redirect or stop. It recommends least-destructive computer recovery and warns that restoring the last saved snapshot can lose recent unsynced work. Hutch should distinguish `waiting_for_answer`, `waiting_approval`, `waiting_human`, `recovering`, and `delivery_failed` from generic “working” or “error,” preserve unsynced work where possible, and make recovery effects visible. ([Troubleshooting](https://docs.x.ai/grok-bot/troubleshooting))

One Grok Bot user reported that running multiple tasks with a primary Bot made it hard to track which task was where; this is an individual organization complaint, not a population measure. Another public discussion raised concern about Bots sharing a computer. The official docs confirm shared files and browser sign-ins but say conversation history stays separate. Hutch’s acceptance should therefore make task lineage, execution state, result delivery, and context-sharing scope explicit, rather than relying on the user to infer which Bot owns a task. ([user report on concurrent-task organization](https://www.reddit.com/r/GrokBot/comments/1wwif7t/how_can_we_make_grok_bot_better_for_you_in_next/), [discussion of shared computer](https://www.reddit.com/r/grok/comments/1w43c1v/grok_bots_own_docs_say_all_your_bots_share_one/))

The docs’ warning about parallel handoff noise is especially relevant: Hutch’s current delegation path can admit a bounded same-Bot child task but does not provide the named cross-Bot coordinator the owner requested. Keep the current hard depth, fan-out, wall-clock, child-count, budget, permissions, and cancellation limits. Treat child execution completion separately from parent delivery: persist a correlated result/status event and retry only delivery, never re-run the child effect merely because a result notification was lost. An execution that succeeded while result delivery failed must remain visible as such. ([Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration), Hutch’s [delegation status](../realignment/delegation.md))

## Hutch product decisions

1. Keep chat as the main work surface. The coordinator is a named, directly conversable workspace Bot; task Bots keep their own chats and can report durable status/results to the coordinator. Users can still start or continue direct conversations with task Bots.
2. Let the coordinator carry forward the current request and only the context explicitly in scope. It drafts clearer outcome-oriented task briefs and asks only about unresolved information. Preserve the original request and provenance; make added assumptions editable and identifiable.
3. Separate prompt from authority. Creating or updating a persistent Bot profile, granting an integration, widening a workspace/context share, and approving an outward action each require their own explicit review; a prompt rewrite cannot authorize them.
4. Keep the roster small. Suggest a new task Bot when a distinct, reusable role exists. Route one-off work to an existing Bot when possible. Keep Fleet searchable and secondary until the roster becomes large; approximately ten Bots is a product-owner starting heuristic, to be checked in visual/usability work.
5. Use durable, structured, correlated handoffs with one owner per stage, bounded fan-out/depth, explicit artifact references, separate execution and delivery states, and lineage-aware stop. Avoid noisy broadcasts and direct peer-to-peer authority; the coordinator is the default routing and return path.
6. Keep credential entry, CAPTCHA/security prompts, and consequential approvals in the same accountable user-to-Bot conversation, with a live human takeover where supported. Never put secrets in ordinary chat or treat a group reply as approval.
7. Turn a one-time task into a saved skill/routine only after it has succeeded and the owner reviews the reusable method, inputs, failure handling, deliverable, and approval boundaries. A saved workflow is persistent behavior and requires confirmation.

## Verification boundary

This review inspected public documentation and selected public user reports on 2026-10-09. It did not create an account, execute tasks, verify an adapter, test the mobile app, or inspect proprietary service behavior. Product statements above are attributed to the official docs; user complaints remain anecdotal. Hutch implementation and fixture/live verification status are tracked separately in `docs/realignment/ledger.md` and `docs/realignment/tests.md`.
