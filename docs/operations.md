# Operating Hutch locally

Hutch is a Linux-first local service. `hutch serve`, `hutch daemon`, and `hutch run` start each run in an owned worker process.
One supervisor lease coordinates scheduling and orphan recovery across web workers and a separate daemon. If the machine sleeps or
the supervisor exits, a later supervisor resumes recovery; an uncertain action is never automatically replayed.

## Start Hutch with your Linux user session

On Linux systems using systemd, `hutch service install` writes a managed `hutch.service` unit under
`$XDG_CONFIG_HOME/systemd/user` (or `~/.config/systemd/user`), reloads the user manager, enables the unit and starts it. The unit
uses the Python environment that ran the command and the current Hutch state directory; by default it serves at
`http://127.0.0.1:8787/`. `hutch service install --port 8788` selects another loopback port. It starts `hutch serve` with remote
access off, and it does not copy shell-only environment variables into the unit. Prefer Hutch's protected key files if a provider
credential must be available consistently to the user service.

Use `hutch service status` to read the user manager's active state and configured local port. That status is systemd process state,
not an HTTP health check. `journalctl --user -u hutch.service` shows service logs. `hutch service uninstall` stops/disables Hutch and
removes only a unit generated by Hutch; the database, saved credentials, assistant workspaces and browser profiles remain. A
hand-edited or unrelated `hutch.service` is left alone. The user service starts with the user manager; Hutch does not enable systemd
linger, configure HTTPS, or make the service reachable from another device. Remote supervision still needs the separately reviewed
`hutch serve --allow-remote` setup described below.

## Linux shell requirements

`sandbox: strict` needs bubblewrap, util-linux `prlimit`, a working user `systemd-run --user --scope`, and permission to create
unprivileged user namespaces. Run `hutch doctor` for the live probe and its error. Strict commands have a private `/tmp`, no
network namespace route, workspace-only writable storage, a 4 GiB address-space and cgroup memory ceiling, a 256-process cgroup
limit, CPU/file/open-file rlimits, a per-command timeout, and bounded captured output. Limits are defaults, not per-bot settings
yet. Hutch is not a virtual machine; the host kernel and read-only system files remain visible.

New bots request strict mode. Existing bots migrated from older versions stay `off`; inspect a bot with `hutch bot show` and set
`hutch bot update <name> --sandbox strict` when the host probe passes. If strict mode is unavailable, the shell tool refuses to
run. `HUTCH_SANDBOX=off` is an explicit operator rollback that disables containment for all bots in that process. Shell network
requests are unavailable under strict mode; use `web_fetch`, which validates and pins the address for each redirect.

## Local workflow qualification

`hutch doctor` is a host and runtime readiness check; it does not qualify a model for workflow
authoring or selection. `hutch workflow qualify <bot> --assess --role author` reports whether the
Bot's current exact profile has probe evidence. Author and selector probes are a separate,
local-owner-only action:

```bash
hutch workflow qualify local-planner --probe --role author --campaign dynamic-workflows-initial
hutch workflow qualify local-planner --probe --role selector --campaign dynamic-workflows-initial
hutch workflow qualify local-planner --assess --role author
```

The initial disposable campaign accepts a loopback Ollama 0.40.3 endpoint and a complete,
installed Q4_K_M profile. It requests 4,096 context and 2,048 output tokens, forces CPU
inference for probes, allows one resident model and one request at a time, and checks available
memory before every request. The runner does not change an existing model residency setting or
install a candidate. Use a private model directory and a separately owned foreground Ollama
process for an evaluation; do not retune a shared service. The durable campaign cap is 80 actual
requests, 60,000 estimated/reported tokens and two hours across roles and candidates. Incomplete
or uncertain requests are not retried and do not grant authority. A successful author/selector
result applies only to the exact profile tested, including decoding and effective context; for
the initial profile, configure the Bot to use a 4,096-token context and the default 2,048 local
turn cap. See [the workflow guide](workflows.md#roles-and-qualification) for probe scope and
failure semantics.

## Workspace continuity

New bots use a new empty workspace per run. To keep files across runs and conversations for one bot, use
`hutch bot update <name> --workspace-mode managed`; this creates a private folder under Hutch's state directory, isolated by the
bot's immutable ID. `--workspace-mode fresh` returns to per-run folders. An existing user folder is explicit:
`hutch bot update <name> --workspace-mode folder --workdir /absolute/path`. The folder must already exist and pass Hutch's path checks.
Changing modes does not copy or remove files. Deleting a bot preserves its managed workspace, and database-only snapshots/restores do not
include managed workspaces or user folders; back these up separately.

Files created through Hutch's `write_file` tool appear as SHA-256-verified downloads in the originating run. Hutch snapshots text files
up to 4 MB each and 16 MB total per run. Shell-created files remain in the workspace and are not attached to chat automatically.

## Stop and incomplete cleanup

Run status remains `Stopping` or `Recovering` when an owned process is still alive or its identity cannot be verified. Hutch records
the process IDs and retries cleanup after the short recovery lease. Do not delete process records or mark a run stopped manually.
Inspect the latest run events and worker log (`hutch bot show <name>` and the bot's `runs/<run-id>/worker.log`). If a host policy
prevents pidfd signalling or process visibility, resolve that host restriction and let the supervisor retry. Hutch will not signal
a numeric PID or process-group ID whose recorded boot/start identity does not match.

## Phone supervision over private HTTPS

Remote access stays off by default. `hutch serve --allow-remote` enables only the paired-phone supervision surface; do not publish
Hutch or use Tailscale Funnel. Keep host firewalls and network ACLs limited to devices you trust. Configure the canonical HTTPS name
as the exact RP ID, origin, and allowed Host before starting Hutch:

```bash
export HUTCH_ALLOWED_HOSTS=hutch-host.tailnet-name.ts.net
export HUTCH_WEBAUTHN_RP_ID=hutch-host.tailnet-name.ts.net
export HUTCH_WEBAUTHN_ORIGIN=https://hutch-host.tailnet-name.ts.net
export HUTCH_TRUSTED_PROXIES=127.0.0.1/32
hutch serve --host 127.0.0.1 --port 8787 --allow-remote
```

Before changing Tailscale configuration, inspect `tailscale serve status` and `tailscale funnel status`; review any existing endpoint
before reconfiguring its port. After confirming the HTTPS listener is available and the effective tailnet policy is restricted, run
`tailscale serve --bg 8787` on the host to proxy Hutch over HTTPS within the tailnet. Recheck both status commands and confirm the
Hutch HTTPS endpoint targeting `127.0.0.1:8787` appears under Serve and not Funnel. Funnel is public when configured, and the same
frontend port cannot be used by both Serve and Funnel. Tailscale's current [Serve](https://tailscale.com/docs/features/tailscale-serve)
and [Funnel](https://tailscale.com/docs/features/tailscale-funnel) pages disagree about whether Funnel is enabled by default, so
inspect the node's actual status and effective policy instead of relying on a default. Hutch also rejects trusted-proxy requests
marked as Funnel ingress, but this guard is defense in depth; do not configure public Funnel access.
New tailnets start with an allow-all policy, so inspect the effective policy and add a grant that limits this host and port to the
operator's devices. Tailscale Serve requires tailnet HTTPS and manages its certificate lifecycle. Enabling tailnet HTTPS publishes
the machine and tailnet DNS name in public certificate transparency logs even though Serve traffic remains tailnet-restricted; choose
names that do not reveal sensitive information. The tailnet grant is a network boundary; Hutch still requires its own passkey login and limits each paired credential
to its Hutch capabilities. Tailscale Serve's current reverse-proxy source sets `X-Forwarded-Host` and `X-Forwarded-For`, sets
`X-Forwarded-Proto: https` when it terminates HTTPS, and marks Funnel traffic; Hutch accepts forwarded metadata only from the
configured loopback proxy peer and rejects the Funnel marker. Hutch continues to require its own passkey session and does not use
Tailscale identity headers as application credentials.

For a local network instead, bind Hutch to one private interface address (never `0.0.0.0` or `::`) and provide a certificate trusted
by the phone. Set `HUTCH_ALLOWED_HOSTS`, `HUTCH_WEBAUTHN_RP_ID`, and `HUTCH_WEBAUTHN_ORIGIN` to the exact DNS name in that
certificate; include a non-default port in `HUTCH_WEBAUTHN_ORIGIN` (for example, `https://hutch.lan:8787`) but not in the RP ID or
allowed Host. Restrict the port at the host and network firewalls. For example:

```bash
export HUTCH_ALLOWED_HOSTS=hutch.lan
export HUTCH_WEBAUTHN_RP_ID=hutch.lan
export HUTCH_WEBAUTHN_ORIGIN=https://hutch.lan:8787
hutch serve --host 192.168.1.10 --port 8787 --allow-remote \
  --tls-cert /path/to/hutch.lan-chain.pem --tls-key /path/to/hutch.lan-key.pem
```

Renew the certificate before expiry and verify the renewed certificate chain, hostname, and passkey origin from the phone before
resuming access. Hutch refuses wildcard and public-address binds.

On the host, `hutch pairing create` prints a single-use code valid for 60 seconds. Submit it only in `/pair` on your private HTTPS
Hutch origin. The code creates a five-minute enrollment-only cookie with a 16-challenge registration limit; if that limit is reached,
request a fresh pairing code. A successful WebAuthn registration creates a separate revocable
passkey credential and eight-hour maximum session. Login requires user verification. Synced passkeys work, so the credential label
is descriptive and does not prove which physical device is using it. Sessions expire after 30 minutes idle or eight hours absolute;
background polling does not extend the idle timeout. The browser clears its private view after expiry or revocation. Logout revokes
that session; `hutch pairing list` and `hutch pairing revoke <credential-id>` inspect/revoke credentials and all sessions for a lost
passkey.

Phone access can monitor Bots, runs, approvals and transcripts; Allow once or Deny a pending action; and Stop or Resume only through
the existing current-event checks. A pairing made with `hutch pairing create --allow-start` adds Start capability, but a local owner
must also enable each Bot with `hutch bot update NAME --remote-start`. Phone starts use the Bot's saved model, tools, workspace and
approval policy. A Bot's pause controls scheduled tasks; an explicit on-demand phone start remains available when both Start gates
are enabled. Revoking the credential or disabling remote starts cancels unclaimed phone work; already claimed runs remain visible and
need an explicit Stop. Device pairing, per-Bot settings, schedules, credentials, provider connections, and all computer interaction
remain local-owner tasks. Uncertain phone command responses require status reconciliation; Retry reuses the original idempotency key.

### Pre-enable acceptance gate

Complete this checklist from an authorized private connection on both iOS Safari and Android Chrome before using remote mode for
real work:

1. Pair with a fresh one-use code, enroll a passkey, lock the session, and unlock with user verification. Confirm private bot/run data
   is absent before unlock and disappears after logout, expiry, and local credential revocation. Leave the page polling past the
   30-minute idle limit once to confirm background activity does not keep the session alive; automated fake-clock tests cover the
   eight-hour absolute limit.
2. Open bot status and a run transcript, then suspend the browser and disconnect/reconnect Wi-Fi or the tailnet. Confirm the phone
   reconciles a fresh snapshot and event cursor without duplicating content or showing stale state as current.
3. Review the exact details for a pending action. Exercise **Allow once** and **Deny** on separate fixture actions, then make a
   competing decision from another session and confirm the losing phone reports the committed decision rather than success.
4. Stop a known run and resume only the current human-wait event. Confirm stale wait controls are rejected after the run advances.
5. Verify a monitor-only credential cannot start work. On a fixture Bot, enable both credential Start and the local Bot setting;
   start one task and confirm it uses the saved model and approval policy. Turn off the Bot setting and confirm another start is
   refused.
6. In a controlled test, interrupt the response after an approval or Start commits. Reconcile with the original request key; confirm
   there is one decision/run and the UI never suggests a new-key resubmission. Do not use a live Bot or external side-effecting tool
   for this check.
7. On the host, inspect `ss -ltnp` and the firewall. For Tailscale, confirm the endpoint appears under `tailscale serve status`,
   not `tailscale funnel status`, and that the effective policy admits only approved operator devices. Test that a non-member or
   unauthorized device cannot connect. For direct LAN TLS, verify the trusted chain and hostname from both phones and confirm the
   host/network firewall blocks every unapproved interface and subnet.

Keep Hutch on loopback if any check fails. Revoke the test credentials and stop the remote-mode process before changing ingress or
certificate settings. Do not use public Funnel, a wildcard bind, or a router port forward.

An operator-managed reverse proxy may be used only when Hutch is configured with its exact proxy IP (`/32` or `/128`) and exact
public host. The proxy must terminate HTTPS, overwrite `X-Forwarded-Host`, `X-Forwarded-Proto: https`, and `X-Forwarded-For`, and
connect to Hutch on loopback. Uvicorn proxy rewriting is disabled; Hutch only accepts forwarding metadata from that configured peer.
Do not configure a broad proxy range. Never trust a browser-supplied forwarding header.

This feature has automated ASGI, route, database, browser-fixture and real-Uvicorn HTTPS coverage. iOS Safari, Android Chrome, live
Tailscale Serve, LAN certificate renewal, and live network isolation have not been validated in this environment; remote access is
not production-certified. The host must remain awake and connected. Remote browser handoff, PTY, and computer input are unavailable.

Local same-session browser handoff is experimental and opt-in per bot; it needs a Linux display and the optional Playwright browser.
Enable **Let me take over this bot’s browser** in the bot setup or settings. When Hutch pauses, read the shown origin and reason,
complete the password, passkey, one-time code, CAPTCHA, or other requested step directly in the visible browser window, then choose
Resume beside the current wait event in that conversation. Hutch resumes the same page in the same bot profile without reloading it,
and checks that the challenge is gone. If the checkpoint remains, Hutch stays paused. Do not paste passwords or verification codes into
chat; Hutch never types them or solves/bypasses CAPTCHA. Ordinary form entries still require action review, and page screenshots are
blocked while a conventional sensitive field is visible. Custom widgets may not be detected. This flow is local Linux desktop only;
phone handoff, remote browser control, authenticated PTY and physical desktop input are not implemented. A headed live third-party
challenge has not been tested.

## Database migration and restore

Before a schema upgrade, Hutch writes `hutch.db.bak-vN` using SQLite's online backup API. The
current schema version is shown by `hutch doctor`. Keep the matching
release and pre-upgrade backups. A normal snapshot captures committed database history, including
WAL pages and accepted event outbox entries; application state not yet committed to SQLite is outside
its scope:

Schema v60 stores accepted event appends in a durable SQLite outbox before returning to the
producer. The batch writer assigns the canonical sequence and hash, then removes the outbox row in
the same transaction. On restart, Hutch restores any accepted rows that had not reached the canonical
event table; they are covered by the database backup and snapshot. An enqueue whose SQLite transaction
did not commit was not acknowledged to its producer.

Schema v46 adds an empty Outlook Mail send-grant table. Upgrade does not copy existing Mail.Read
grants into it; Mail.Send always needs a separate sign-in and owner grant. Older releases cannot
enforce the new approval or uncertain-send rules, so restore the matching pre-upgrade backup before
rolling back the application.

```bash
# Replace STATE, SNAPSHOT and STATE_RESTORE; both destination directories must be new.
HUTCH_STATE_DIR=STATE hutch state backup SNAPSHOT
# Or convert an existing pre-upgrade backup to a manifest-backed snapshot:
HUTCH_STATE_DIR=STATE hutch state backup SNAPSHOT_OLD --database STATE/hutch.db.bak-vN
hutch state restore SNAPSHOT --to STATE_RESTORE
HUTCH_STATE_DIR=STATE_RESTORE hutch status
HUTCH_STATE_DIR=STATE_RESTORE hutch state report RESTORE_ID --limit 100 --offset 0
```

The restore validates copied bytes, integrity, transcript chains and immutable action intents;
migrates offline; quarantines old unfinished work; revokes devices/standing grants; pauses
schedules; and rotates resource history's epoch. It detaches source process records without
signalling them or pretending cleanup occurred. The original installation and snapshots remain
intact. Normal startup refuses incomplete restores and direct use of a snapshot as executor
state. Inspect report pages until their full scope is reviewed. The web header also explains the
hold; new chat submissions preserve their draft and return `restore_review_required`.

Before production cutover, stop the original Hutch services and verify their owned executions
have stopped. Review effects/charges after the snapshot, uncertain receipts, provider records
and excluded files. Preserve credentials/connection files, browser profiles, workspaces,
artifacts and filesystem transcripts separately; a database-only snapshot does not archive
them. Its prompts/arguments/evidence can contain private material. Check user-owned `workdir`
references before allowing new tasks to use them. Restart services on the verified installed
release, never a mix of already-loaded old modules and newly installed code. Then record a
local operator review using the restore ID printed by the command:

```bash
HUTCH_STATE_DIR=STATE_RESTORE hutch state activate RESTORE_ID --evidence 'Record what you actually checked'
```

Activation rechecks integrity/history, the installed executor/UI fingerprint and absence of
unexpected runnable work, then resolves once. It allows **new** explicit work; old work stays
quarantined and device/standing grants revoked. Activation does not unpause saved schedules;
an operator may explicitly change their paused setting during review. Re-pair devices and restore
needed grants deliberately. If installed executor/UI bytes changed since validation, restore
with that release into another new directory. Configure the service to use the reviewed state
directory only after cutover checks; the CLI does not switch your service configuration.

## Auditing run transcript integrity

Every newly written run event is linked into an ordered SHA-256 chain. Inspect an individual run from its detail page or verify it
from the terminal:

```sh
hutch runs verify <run-id>
```

An intact chain exits successfully and reports the number of events checked. Older events written before hashing are reported as
**partial** because their original links do not exist; Hutch cannot prove their historical integrity. A changed or missing event fails
verification, and the CLI exits with status 1. Verification is read-only: it does not repair, delete, or rewrite the transcript. Keep
the original database intact and make a separate backup before investigating a reported mismatch.

## Reviewing an OpenCode coding task

When a completed Studio answer offers **Prepare coding task**, review the original request and edit the suggested brief before
confirming. Preparation is available only when the Bot's configured workspace is an existing Git repository and the OpenCode CLI
is installed on the Linux Hutch host. The first time, connect a provider in an interactive terminal on that host:

```sh
hutch code login
```

OpenCode presents its supported provider sign-in picker. Hutch stores that provider connection in a dedicated private profile
under Hutch's state directory. It does not copy or inspect credentials in your regular OpenCode profile. OpenCode Go's provider
connection remains a separate API-key flow. After connecting a provider, run the exact command shown on the task card:

```sh
hutch code run <task-id>
```

The command checks the private profile, creates a separate Git worktree at the reviewed commit and opens the installed OpenCode
mini interface. Select the model in OpenCode. Its provider usage is separate from Hutch's account records and budgets. Review
every OpenCode permission prompt: commands you approve run with your Linux
user’s file, process and network access and do not pass through Hutch’s bubblewrap shell boundary. Do not include credentials in
the task. The branch is retained for you to inspect; Hutch does not apply, commit, push or publish it.

OpenCode runs in a separate process group inside the current terminal session. Hutch temporarily gives that group foreground
terminal input, waits for it to exit, verifies and ends any remaining processes in its group, then restores terminal input to
Hutch. Before launch, Hutch checks for Linux pidfd-based process identity support and refuses hosts that cannot verify it.
Pressing Ctrl+C sends an interrupt to OpenCode's foreground group; Hutch records a stopped outcome only after cleanup is
verified. This preserves interactive terminal behavior while allowing bounded cleanup; it is not a sandbox for approved shell
commands. If Hutch cannot restore terminal control or verify cleanup, leave the task card visible and inspect the terminal before
trying again.

If terminal interruption reports that process cleanup could not be verified, leave the card visible and do not relaunch the task.
Inspect the local terminal and task branch, then run `hutch code reconcile <task-id>` only after the OpenCode process group
has exited. Reconcile never sends a signal; if boot/PID identity or process-group disappearance cannot be proved, it leaves the
task active for review. Task records and immutable project identity are stored in schema v39; normal SQLite backup and restore
retain them. Restoring state does not copy or remove the Git worktree, which must be managed separately.

The local command is not a remote API worker. Launching a coding task may consume the connected provider's quota; Hutch does not
account for this usage. The version/help and saved-connection checks make no model call. OpenCode keeps provider secrets in its
SQLite database at `opencode-profile/opencode.db` under Hutch's state directory. That separate database is not included in
Hutch's SQLite-only state backup; after restoring Hutch state without the profile database, connect a provider again with
`hutch code login`. Protect the profile directory as account credentials.
Never claim a Hutch hard spending limit for these tasks.

### Common handoff errors

- **OpenCode is not installed or has no interactive `mini` command:** install a supported OpenCode CLI on the Hutch host and
  retry preparation. Hutch checks the version and required commands before use; the OpenCode agent-config loading and live
  model behavior have not been verified.
- **No provider is connected to Hutch's private OpenCode profile:** run `hutch code login` in an interactive terminal on the
  Linux host. The browser chat cannot start a terminal or complete this provider sign-in for you.
- **Configure the repository root:** select the Git worktree root as the Bot's existing folder. Hutch records the commit at
  preparation time; later source changes are not copied into the task.
- **Project contains OpenCode plugin files:** the handoff refuses to start while `.opencode/plugins` or `.opencode/plugin`
  exists, because a reported OpenCode behavior may load local plugin code despite isolation flags. Review/remove that project code
  yourself only if it is appropriate for your project; Hutch will not bypass this guard.
- **Cleanup could not be verified:** do not prepare another attempt or remove the worktree. Check the original terminal and
  process group, then run the read-only reconcile command. A reused PID or a changed host boot identity is never signalled.

## Change-feed retention

The elected scheduler supervisor keeps at most 50,000 content-free `/api/v1/changes` invalidations,
checking every five minutes. If a long-disconnected client presents a cursor older than the retained
boundary, the page or stream asks it to fetch a bounded `/api/v1/snapshot` and resume from that
snapshot's `change_cursor`. This only prunes invalidation hints; it does not delete conversations,
messages, approvals, run transcripts or event history. Transcript/global-event retention is a
separate, currently unbounded policy.

A new resource epoch forces stale clients to reconcile a rewound history. Existing numeric
transcript cursors lack this protection: close/reload clients after restore. Direct replacement
of a live database is unsupported. If a command failed, preserve its incomplete directory and
error, repair the cause and retry into a new destination; do not delete its marker to force
startup. Snapshot hash mismatch/SQLite sidecars require a new closed snapshot. Unexpected
execution while held or invalid history requires inspection rather than requeueing. Hashes are
integrity checks, not signatures or external-effect evidence. No production restore or hardware
power-loss certification has been performed here. See [ADR-0015](adr/0015-held-database-restoration.md).

Schema v12 reconstructs missing files from committed database events after startup. Existing
partial, changed or ahead-of-restored-history files are retained as
`transcript.preserved-*.jsonl`; inspect those copies before removing them. Do not replace an
invalid canonical database with a file mirror automatically. The run API/UI reports pending
delivery or an error while continuing to show canonical database history. Check disk space,
ownership and link errors, repair the private state directory, then let delivery retry.
SQLite uses FULL WAL synchronization; this does not certify hardware power-loss behavior.
See [ADR-0013](adr/0013-recoverable-transcript-files.md).

For **Action outcome needs review**, open the card in chat or the paginated **Needs you** drawer.
Inspect its saved arguments and authority; legacy receipts explicitly lack original arguments.
Check the file, account or service involved before selecting an outcome and recording evidence.
Recording a checked outcome performs no action and grants no permission. The original run status,
receipt and transcript remain unchanged; the UI labels the result a human report. Retry an uncertain
response with the retained report. Another client's prior record conflicts rather than overwriting it.
Do not treat a Done label on a migrated historical run as proof of a missing legacy receipt.
These commands are also available through the typed
[`/api/v1/actions/receipts` contract](realignment/contracts.md#action-receipt-review-schema-v13).

Keep the backup until the restored database opens and expected bots, runs, approvals, transcripts, conversations and messages are present. A backup from an
older schema will migrate forward on open, creating its own versioned backup first. Rollback to older Hutch code requires restoring
the matching pre-upgrade backup; older code does not honor leases or fencing. Validate restoration against a copy before using it
for production state.

Schema v8 gives every pre-existing run a separate imported legacy conversation. Schema v9 adds single-use pairing codes and hashed,
revocable sessions; schema v11 adds content-free transactional invalidations and history cursors;
schema v12 backfills recoverable transcript-file delivery without changing historic run IDs;
schema v13 retains immutable action intents and separate checked outcome reports.
Schema v14 records restore review and detached process identities without transferring source
execution authority.
Schema v15 preserves legacy memory values as unreviewed legacy proposals, without guessing a
private chat or treating a prior `user` label as approval. Review an exact revision before recall;
sharing it across a bot's chats requires an explicit decision. Rollback uses a compatible release
and its matching backup, rather than restoring automatic injection of old facts into prompts.
Schema v16 removes per-event transcript-mirror triggers. The event writer records one durable
delivery intent per committed batch in the same transaction as canonical event rows; upgraded
installations preserve pending delivery state and their pre-upgrade backup.
Schema v17 adds explicit cross-chat artifact references. A share is a durable database grant; it
does not copy bytes into the target workspace or conversation context. Its target-specific download
URL stops working after revocation, while the source run's own download remains. The originating
chat lists active recipients and can revoke a grant; the receiving chat can also stop its access.
Schema v18 adds transactional source-chat invalidations when a share is granted or revoked, so open
source Files views refresh after changes from another device. Keep the matching pre-upgrade backup
until the upgraded application and shared-file list have been checked.
Schema v19 records one versioned Resume per `human_needed` event sequence. The route checks that
the run is still waiting under a live owner lease and that the submitted sequence is the current
wait; exact retries return the stored response without setting the resume flag again. Existing
unversioned resume routes remain for compatibility and do not carry this stale-event guarantee.
Schema v20 assigns each recurring task its own occurrence claim stream while retaining the first
task through the legacy `schedule` alias. Schema v21 creates a durable identity registry; removed
schedule IDs stay reserved even if the task never fired, and deleting a bot does not erase that
task identity. The migration backup can be restored with the standard held restore procedure above.
Schema v22 records immutable same-bot run lineage; v23 stores the delegated subtree currency ceiling;
v24 captures an immutable, credential-free capability snapshot when a root run starts and copies it
to internal children. Existing runs receive no invented delegation budget or capability snapshot, so
they cannot admit delegated work. New child work is available only through the explicitly enabled
`delegate_task` tool on a supervised built-in Strict Offline run; every request asks for approval,
even when the bot is configured for auto approvals. Child instructions and execution permissions
come from the root snapshot, but prior conversation messages and parent workspace contents are not
copied. The child gets its own private 0700 run workspace and its run/artifacts stay visibly
attributed to that child in the shared conversation. No automatic workspace transfer occurs.
Lineage admission is idempotent and bounded; an exact retry from the same tool step reuses the child.
Stopping a run persists cancellation for its descendants before cleanup starts; each
process-owning run remains Cancelling until its own process group has been verified gone. This
preview requires the process executor and verified Linux Strict Offline prerequisites; it does not
enable Pi/OpenCode child runs or parallel child tool calls. See
[`realignment/delegation.md`](realignment/delegation.md) before enabling it.
Schema v39 adds immutable, idempotent local OpenCode coding-handoff records and content-free change notifications. The reviewed
Git project identity and source chat references migrate in the SQLite database; task worktrees and OpenCode's private profile
database are separate files and are not included by database-only backup. The OpenCode profile contains provider credentials;
keep it private and reconnect after a restore if it was not separately retained. See [Reviewing an OpenCode coding task](#reviewing-an-opencode-coding-task).
Hutch does not infer that adjacent runs share a
private context. New conversations and message submissions are written transactionally with their idempotency records. The
`conversation_fts` index contains message text only; it excludes tool output, credentials, workspaces and bot memory.

## Limits and evidence boundaries

Hutch's currency checks reserve a recorded-price estimate using its prompt-size estimate and requested reply-token cap. They are
admission limits, not a guarantee against provider billing differences. Configure an independent limit with the provider when you
need a separate external ceiling; do not treat Hutch's estimate as an exact dollar cap.
The product support and verification matrix is in [the realignment ledger](realignment/ledger.md). Provider calls, real local models,
Pi/OpenCode, browser binaries, mobile hardware, and physical desktop portals are reported separately from fixtures.

## Reference fact review and troubleshooting

In a bot's chat, ask it to remember a reference value. An enabled memory tool saves a proposal
for that chat, shown below its attempts. Review the exact value and scope. Keep sharing unchecked
to retain the chat boundary; explicitly share only when other chats for this bot should recall
that value. Review grants no tool permission and does not prove a fact true. Attempts outside a
canonical conversation have an isolated run scope. The model retrieves reviewed references through
`recall`; facts are not automatically injected into the system prompt.

For empty recall, check that memory is enabled, the current revision is reviewed, and its scope
matches the chat. Search uses bounded literal word terms, not arbitrary FTS operators or substring
matching. A replaced revision conflicts at review: close the dialog, refresh and inspect the new
value. Legacy proposals need explicit sharing or a new scoped revision. Oversized legacy values
need an explicitly shorter proposal. A shared key conflict requires inspecting the existing bot
reference before revising or archiving it.

Bot settings provide paginated active and archived records, revision history and human review
records. Disabling memory prevents new runtime proposals/recall and removes tools from new lists;
human management stays available. It cannot retract content already sent to a provider or erase
previous conversation/tool history. Never store credentials in reference facts.

`hutch bot forget NAME --key KEY` archives all scopes and versions with that key for the bot.
Without a key it archives all reference facts and revokes standing tool grants. Archive retains
history, the search index and backups; permanent scoped deletion is not implemented. To download
portable memory, open that Bot's settings and choose **Download memory JSON**. The bounded export
contains all revisions/scopes, review records and explicit incoming/outgoing share snapshots. It is
unencrypted plaintext; fact values and review notes can contain personal or sensitive information. It excludes conversations,
credentials, run events, action receipts, workspace files and artifact bytes. A separate all-Bot memory
page is deferred; direct settings are the owner-facing inventory for each Bot. Deleting a Bot archives
its facts and leaves a user-owned workspace intact.

## Generated documents

Documents created through the `create_document` tool are stored under `<state>/documents/` as immutable,
hash-recorded versions (`<doc id>/vNNN-<sha8>/`). Bounds are engine-enforced: 32 MB per document, 16 documents
per run, at most 60 rendered preview pages at up to 1600 px, and ZIP bundles capped at 512 entries and 64 MB
uncompressed. There is no automatic deletion of promoted versions in this release; abandoned staging is
reconciled at startup after its owning job is gone, and promoted versions without a committed row (a crash
between promotion and the database write) are deleted because they were never visible. Backups should include
the `documents/` directory beside `hutch.db`.

PDF page previews render locally with the bundled PDFium binary. Layout previews for DOCX/XLSX/PPTX additionally
need LibreOffice (`soffice`) installed; each render job gets a fresh LibreOffice profile, a 120-second wall clock
and an owned process group, and the app degrades to structure previews with an honest state when the binary is
absent. Run `GET /api/v1/documents/readiness` to see which formats and preview modes are available on this host.
