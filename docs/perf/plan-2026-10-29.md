# Performance engineering plan (D5) - 2026-10-29

Status: adopted 2026-10-29. Owner: Lead. Gate: every adopted change needs a measured
before/after on the same machine and session, plus focused regression tests; no Rust
adoption without clearing the repository P11 bar (docs/realignment/desktop-production-2026-10-26.md):
additional Rust performance replacement only after equivalent tests and
>=20% p95 or >=30% memory improvement including IPC.

Machine: AMD Ryzen 3 5300U (4C/8T), 22 GiB, Linux 7.2.x, Python 3.13.15, Rust 1.97.1.
Load caveat: host load average was 7-14 during the baseline (other sessions outside
our PID namespace), so absolute timings are inflated and CV is 20-30% for ms-scale cases.
Decisions therefore use operation-level ratios (paired A/B where possible), not cross-day
absolute comparisons. Baselines: benchmarks/results/hotpaths-2026-10-30.json (commit de890972).

## 3. Adopted work order (small, independently reviewable commits)

1. `perf(toolcalling)`: schema analysis/validator cache; validate.py split; focused tests
   (tests/test_toolcalling_validation.py, compiler/properties tests, new cache tests).
2. `perf(runtime)`: transcript token-accounting cache; context/fitloop split if needed;
   tests for equivalence, bounds, overflow, empty transcripts.
3. `perf(server)`: SSE global-stream byte framing; sse resume tests; JSON equality tests.
4. `perf(bench)`: repair the stale benchmarks.run step-overhead metric (HUTCH_TESTING mock
   runtime was removed at HEAD; it currently records 0.0 ms) with the tests' deterministic
   fake-provider pattern; re-record the local baseline after verification; update docs.
5. `native(docgen)`: optional Rust xlsx write kernel prototype + A/B measurement; adopt or
   reject with recorded evidence (D7).
6. `docs(performance)`: measured before/after table, method, variability, honest limits,
   append-throughput trade-off, deferred frontend/startup follow-ups.
7. Visual validation (D9): browser smoke against seeded state for dashboard/run pages;
   no UI source changes expected, so this is a regression/visual-integrity gate, not a redesign.

## 4. Pre-registered acceptance thresholds

- A validation: median validate_call_valid <= 44.7 us (>=30% below 63.8 us) and p95 <= 60.5 us (>=30% below 86.4 us); identical problems for invalid corpus and full toolcalling tests green.
- B token accounting: cumulative 100-step token sizing <= 14.7 ms (>=50% below 29.4 ms); prompt_tokens/count_tokens outputs byte-identical on the fixture corpus.
- C SSE frame: median 200-event frame <= 0.443 ms (>=20% below 0.554 ms); decoded JSON identical to the old shape.
- D Rust xlsx: total p95 for 5000-row generation <= 252 ms (>=20% below 315.3 ms) measured through one Python driver including the kernel boundary, with the Python fallback byte-valid and all docgen tests green; if not reached, record reject-measured.
- Global: no regression in `python -m benchmarks.run --check`, focused pytest for every touched module, audits green.

## 5. Constraints and non-goals

- No changes to execution/approval/security boundaries; no new network egress; no schema or refusal-text changes.
- Do not touch main checkout/parked files; work only in the perf-rust worktree; explicit-path commits.
- Do not weaken event durability for throughput (E), do not target free-threading (research 1.3), no second executor.
- Frontend and startup candidates are deferred with measured evidence and concrete follow-up specs, not silently dropped.
