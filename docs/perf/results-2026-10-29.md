# Performance programme results (2026-10-29)

This is the measured record for the 2026-10-29 performance-engineering and selective-Rust
programme. Plans and external research are in `docs/perf/plan-2026-10-29.md`,
`docs/research/performance-rust-2026-10-29.md` and ADR-0024. Numbers are measurements on one
machine; they are not product guarantees. Anything not measured is labelled unverified.

## Method and environment

- Host: AMD Ryzen 3 5300U (4C/8T), 22 GiB RAM, no GPU, Linux 7.2.x, Python 3.13.15.
- The host is shared: load average ranged from 2.2 to 14 during this work (other sessions
  outside this sandbox). Absolute ms values therefore move between sessions. Decisions below
  use paired comparisons in one process/session; only those paired deltas are claims.
- Harness: `benchmarks/hotpaths.py` + `benchmarks/hotpath_workloads/` (commit de890972),
  isolated `HUTCH_STATE_DIR` per case, n/min/median/p95/max/CV, load average, machine identity
  and harness digest recorded in JSON. Reproduce:
  `PYTHONPATH=$PWD/src .venv/bin/python -m benchmarks.hotpaths [--quick] [--only NAMES]`.
- Existing gate: `python -m benchmarks.run [--check]`; the PF-11 step-overhead fixture was
  repaired (see below) so it measures the deterministic scenario runtime again.
- Profiling: cProfile top-30 cumulative/tottime for the real engine step, event serialization
  and context sizing; artifacts are in the long-horizon ledger, not the repository.

## Real-world and scale validation

- Dashboard API at scale (60 bots, 10,000 events, isolated state, real app via TestClient):
  snapshot 229 KiB p95 18.8 ms, roster 105 KiB p95 35.9 ms, per-run event page 500 events
  p95 8.9 ms, change feed 32 KiB p95 5.0 ms (quiet-baseline session).
- XLSX generation 5,000 rows: median 265.6 ms, p95 338.4 ms (quiet-baseline session; the
  independent openpyxl read-back gate is ~59% of it). 500 rows: median 34.8 ms.
- Deterministic engine scenario with real policy/tool/event path: step-overhead measured
  0.41-0.97 ms per step after the fixture repair (previous mock-based claim 0.25 ms was stale).
- Browser validation of the SSE/event path: real FastAPI app with 20 bots and a 120-event run;
  headless Chromium 153.0.8010.12 at 1440x900, 900x900 and 360x800. No page errors, no
  horizontal overflow, run page renders the seeded prompt; the browser's EventSource decoded
  the 120-event replay frame and a live event appended while viewing (1 new frame, cursor
  advanced 120 -> 121). Screenshots and JSON capture are in the programme ledger.

## Documented non-adoptions and deferrals

- **Rust XLSX write kernel (measured, rejected/deferred).** A disposable PyO3 0.29.3 +
  rust_xlsxwriter 0.90.2 prototype wrote a 5000x3 workbook in 24.1 ms median; the Python
  `_write_workbook` stage costs 108.7 ms of the 296.6 ms generation total. The operation-level
  gain (~28% before boundary copies) would clear the P11 threshold, but adoption was rejected
  for this release: a shippable wheel needs packaging/manifest changes that are another
  session's uncommitted work; an unshipped optional `.so` does not improve the product; the
  independent read-back gate (59% of the cost) must stay independent; and the end-to-end effect
  is tens of milliseconds on unusually large documents against model drafting time. Revisit
  conditions are in ADR-0024.
- **Event append throughput.** Measured 5.4-6.2k events/s now versus the 52k/s recorded in the
  2026-10-07 baseline. This is a deliberate crash-recovery trade: `append_event` commits a
  durable outbox row per accepted event so an accepted append survives restart. The documented
  sustained gate is 1,000 ev/s (more than 5x headroom) and real event rates are far lower. The
  outbox contract was not weakened for a benchmark.
- **CLI cold start (deferred).** Under `-X importtime`, `hutch.tools` import costs ~294 ms
  cumulative (synthesis 111 ms, media 81 ms) and `hutch.cli_bot_deletion` ~196 ms, even for
  `hutch version`. Lazy command/tool imports could plausibly cut this, but the CLI is a
  2,758-line frozen file and the tool catalog contract needs its own focused change; recorded
  as a measured follow-up rather than rushed into this programme.
- **Dashboard render amplification (deferred, measured design work).** The UI is bounded at
  10k events, but every SSE batch triggers a 250 ms-debounced refetch of `/api/runs/:id`
  followed by a full `innerHTML` replace; the chat feed runs six sequential API calls and
  re-renders all six run blocks. Incremental append / using the SSE payload would be the
  largest user-visible win, but `app.js`, templates and static sources are another session's
  uncommitted parked work and cannot be merged safely in this window. The exact acceptance
  surface, measurement recipe and task spec are recorded in
  `docs/research/artifacts/perf-2026-10-29/ui-acceptance-surface.md`.
- **Other Rust candidates.** JSON/SSE serialization is pydantic-core (already Rust) plus
  stdlib C JSON; streaming assembly is linear (~29-33 MB/s, 7 ms for a rare 200 KB argument
  stream); SQLite and sqlite3 are C and API pages are bounded; the orchestrator is
  pre-rejected by ADR-0001/0016. None can move the measured p95 or justify a new native
  boundary; details and measurements are in ADR-0024 and the plan.

## Honest limits

- Absolute timings are noisy on this shared 4C/8T host (CV 8-30% for ms-scale cases). The paired
  deltas above are reliable because both sides ran in the same session/process; cross-run
  absolute numbers should not be compared.
- The benchmark harness measures control-path CPU, not model latency. A faster validator or
  token counter does not make a model reply arrive sooner; it reduces Hutch's own CPU cost and
  battery use, and the SSE/token changes reduce replay/render pressure at scale.
- The browser validation is a regression/integrity gate (no UI source changed); it is not a
  before/after visual claim for the deferred frontend work.
- The Rust prototype was a disposable feasibility measurement, not shipped code; its numbers are
  recorded here rather than reproducible by a committed harness.
