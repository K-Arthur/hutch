# Marketing site claims and evidence

The static site is an alpha preview, not an installation or hosted-service funnel. Its source repository is private and there is
no public package or release. The anonymous page therefore points its calls to action to local sections that show the demo and
availability status; it does not send visitors to a private GitHub repository, copy commands that cannot work anonymously, or
contact the Hutch host. The site loads its CSS, JavaScript, font and images from its own directory. No browser preference is
stored: motion follows the operating system's reduced-motion setting automatically.

## Capability language

| State shown publicly | Evidence and limit |
|---|---|
| Supported | Linux execution, local SQLite state, deterministic offline mock and fixture-tested lifecycle/API paths. This does not imply a public download or production service. |
| Experimental | Configured hosted-provider and local-inference routes. Provider HTTP behavior has fixture coverage; no paid provider or real Ollama model was exercised for this release. |
| Unavailable | macOS/Windows executor, public source/package, remote phone control, browser handoff, OpenCode/Pi harness execution and Sign in with ChatGPT. |

The site distinguishes the control state kept on the host from prompt traffic to a selected model and network traffic generated by
tools. Hutch reserves token and price estimates before eligible hosted calls. Those estimates are not guarantees of provider
invoices; operators should use provider-side billing controls for external spending limits. Bubblewrap is an optional Linux
namespace sandbox, not a VM; migrated bots remain unsandboxed until an operator enables it.

## User-report scenarios

The receipts section links directly to three public issues used as acceptance scenarios, not as prevalence evidence:

- [OpenClaw issue 138499](https://github.com/openclaw/openclaw/issues/138499): one report of a timed-out scheduled task remaining marked as running and delaying restart. Hutch tests keep cancellation visible until owned execution exits and fence expired ownership before recovery. The report itself says its reproduction conditions were not sufficiently deterministic.
- [Open WebUI issue 30055](https://github.com/open-webui/open-webui/issues/30055): one report that a full-screen mobile call overlay hid an already-delivered approval. Hutch keeps approval state and decisions in the responsive app and fixture-checks phone layouts; this is not a physical-device certification.
- [Open WebUI issue 31656](https://github.com/open-webui/open-webui/issues/31656): one report that mobile menu focus opened a text field and keyboard unexpectedly. The Hutch menu uses dialog focus, Escape and focus restoration checks. This is keyboard/viewport coverage, not a screen-reader audit.

The site intentionally removed unattributed forum IDs, unsupported spend-guarantee language, claims that every path is jailed, dead public-install links and claims that disabled external harnesses are supported.

## Build (Tailwind v4 + DaisyUI v5)

The marketing surface is Tailwind + DaisyUI layered on the brand token source:

- `website/src/input.css` — Tailwind v4 entry. DaisyUI v5 loads with an explicit component
  include list (`button, badge, card, navbar, footer, table, collapse, alert, link, menu`)
  and a custom `hutch` theme mapped to the pinned brand contract: emerald `#34d399`, 0px
  fields (buttons), 100px selectors (badges/chips), 8px boxes (cards/panels), one dark theme.
- `npm run build:css` compiles `website/app.css` (29-49 KiB minified, within the 40 KiB CSS
  budget at the trimmed include list). The built file is committed so the page stays
  static: no runtime external requests, no build step needed to serve it.
- `website/styles.css` holds only hutch-specific pieces — hero weave, proof chrome, code
  window, architecture diagram, receipts/availability tables, footer base, motion.
- `website/tokens.css` remains the generated source of truth for brand/semantic values;
  `tests/test_site_tokens.py` checks that every `var(--token)` in `styles.css` resolves, and
  that the compiled `app.css` is present with the theme and components in place.

## Reference decisions (supplied design set, Oct 2026)

Adopted: window chrome for product proof (traffic-dot trio, centred monospace title, status chip); the receipts as a real
data table (# / Source / Reported failure / hutch answer / Evidence) with fixed columns, hairline rows, right-aligned
evidence pills and a mobile card stack; icon + title + copy feature cards in a three-up grid; a separately headed
"How a run is wired" architecture block (SVG diagram on desktop, readable list on phones) kept apart from the feature cards;
data-first workflow cards (capture on top, number + title + one-line caption); a model-route pill row; the poster wordmark
sized to sit fully inside its column (no sliced strokes) behind a dimensional subject with exactly one front glyph; a
monospace spec line under the hero subject; and syntax-coloured code windows (chrome bar, coloured keys, terminal status bar).

Rejected: purple aurora gradient heroes, gradient display type, warm-beige editorial palettes, collage-of-floating-cards
backgrounds, and the 24-48px translucent container look. Also rejected after review: a page-level emerald hero wash (removed
in favour of the artwork's own contained glow), a box-in-box "limits" panel with an orphan card (now a plain hairline list),
a half-empty wide use-case card (now three even columns), a container wrapped around the receipts table, and a poster wordmark
cropped past the scene edge. The pinned brand contract (emerald accent, 0px controls / 8px panels / 100px chips, one dark
theme) governs.
