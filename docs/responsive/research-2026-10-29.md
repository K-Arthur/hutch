# Responsive adaptation - Phase 0 online research

Date: 2026-10-29. Author: research teammate (read-only source investigation).
Surfaces in scope: dashboard SPA (`src/hutch/server/static/index.html`),
server-rendered pages (`src/hutch/server/templates/`), and the static marketing
site (`website/`). This report writes nothing except this file.

Working-tree note: another session's uncommitted brand/dashboard changes are
present. All `file:line` citations describe the working tree as observed on
2026-10-29; line numbers may drift when that work lands.

## Methodology

1. Read `AGENTS.md`, `DESIGN.md`, `docs/design-system.md`,
   `docs/marketing-site.md` for stated responsive requirements.
2. Inventoried hand-written responsive primitives with ripgrep, excluding
   generated CSS (`ui.css`, `model-switcher.css`, `website/app.css`,
   `website/styles.min.css`): 161 `@media` blocks, 19 distinct `max-width`
   thresholds, 1 `@media (hover: ...)`, 3 `env(safe-area-*)` uses, 179
   `44px` declarations, 7 `@container` blocks, one presentational platform
   sniff (`app.js:3636`) and no touch-event branching or UA-gated layout.
3. Reviewed the Playwright e2e viewport matrix (Chromium only) to find which
   device classes are actually exercised.
4. Web research against primary sources (WebKit, MDN, W3C, web.dev, Apple
   device reference, industry UX metrics). Every source was fetched and read on
   2026-10-29; claims below are limited to page text that was read. No emulator
   run, device session, telemetry, or production data was available.

## Findings

| Topic | Source | Finding | Implication for Hutch: file/surface |
|---|---|---|---|
| Missing viewport meta is a silent whole-site failure | S1 post-mortem, S17 | In the incident write-up, a production WordPress page shipped without the viewport tag; mobile browsers used a ~980px layout viewport, so every width breakpoint fired against the wrong width and the whole site rendered as a shrunken desktop page. No error, no console message. | Three shells must be asserted independently: SPA `src/hutch/server/static/index.html:5` has `viewport-fit=cover`; server pages `src/hutch/server/templates/base.html:6` and marketing `website/index.html:5` lack it. Nothing in e2e checks the tag, so a new template can lose it silently. Add a template/shell assertion. |
| iPadOS reports a desktop UA | S3, S4 | Safari on iPadOS sends a user-agent string "identical to Safari on macOS" (WebKit, Safari 13; iPad mini was the stated exception then); UA sniffing is explicitly documented as unreliable and a source of bugs. | Do not introduce UA-gated layout. Use `pointer`/`hover`/`any-*` plus width and height. The only platform sniff is presentational and safe (Cmd vs Ctrl hint, `app.js:3636`); the touch-visible failure mode is `title=""` tooltips and hover styling (see below). |
| 1366x1024 "square" iPad landscape class | S16, S3 | iPad Pro 12.9-inch and iPad Air 13-inch are 1024x1366 logical points (landscape 1366x1024, 2048x2732 at 2x). iPad Pro 13-inch (M4/M5) is 1032x1376 points (landscape 1376x1032). Layout height is then reduced by Safari tab bar / toolbar chrome. | A 1366-wide iPad gets Hutch's *desktop* shell: full 272px sidebar (304px above 1000px, `app/src/input.css:39-43`), 32px icon buttons, desktop paddings, but a touch screen. The 901-1400px band is where the two shells disagree: the SPA shows the sidebar and only switches to overlay nav at <=900px (`style.css:1680-1694`), while server pages switch at <=1400px (`hutch.css:331-343`, `hutch.js:188`). Same device, two navigation models. |
| Width-only breakpoints vs continuous window sizes | S18, S16 | iPadOS Split View / Slide Over / Stage Manager resize windows independently of device, so window width is continuous, not a device class. Resizing Safari also re-evaluates width/height media queries live. | Breakpoints are width-only and clustered at 640px (36 uses), 560px (10), 480px (8), 900px (9), 940px (7), plus 1400px (server-page nav only) and 1100px families; only heights 760/520px are queried at all (`studio.css:776-797`). Intermediate iPad window widths (roughly 500-1300px) are untested. Prefer container queries where the pane, not the window, is the constraint; `style.css:2182-2199`, `studio.css:687/767/914/965` show the pattern already works here. |
| 100vh and dynamic browser chrome | S7, S8, S2 | `100vh` does not change when mobile toolbars retract/expand, so 100vh elements are too tall on load and bleed under browser UI (web.dev). WebKit bug 141832 (2015, resolved as configuration) records the same: interface bottom hidden behind the browser bar. `dvh/svh/lvh` exist for this; Safari supports them from 15.4. | Server-rendered pages still use `body { min-height: 100vh }` (`src/hutch/server/static/hutch.css:57`); SPA shell already uses `height: 100dvh` with a `100vh` fallback (`style.css:237-239`). Mixed units mean the SPA resizes with toolbars while server pages can push the footer/toolbar off-screen. Standardize on `100svh` for minimum height and `100dvh` for app frames; keep a `100vh` fallback for old engines. |
| Keyboard shrinks visual viewport, not layout viewport | S11, S3 | The on-screen keyboard can shrink the visual viewport without changing the layout viewport; visualViewport events expose the change. WebKit added Visual Viewport API with desktop-class iPad browsing. | Popup placement already listens correctly: `controls.js:48-73` positions with `visualViewport.offsetTop/width/height` and `controls.js:185-188` repositions on visualViewport resize/scroll. But the app shell, composer, modal sheets and bottom bars have no visualViewport handling; a fixed bottom composer can be covered on iOS. Add keyboard-aware checks for the composer and sheets. |
| Hover-dependent UI on touch | S5, S6, S3 | `hover: none` means the primary input cannot hover (or only emulates it by long-press); touch is typically `pointer: coarse / hover: none`. iPad with a trackpad can change the *primary* pointer, so `pointer`/`hover` can flip mid-session. | Only one hover-gated rule exists (`style.css:1850-1853`), and it is correctly scoped to `(hover: hover) and (pointer: fine)`; roster options stay visible/tappable because their base state is `opacity: .62; pointer-events: auto` (`style.css:1842-1843`). Residual risk: 151 bare `:hover` selectors across the dashboard, brand and marketing sources produce sticky hover on touch, and icon-only controls rely on `title=""` tooltips (e.g. `base.html:57`) that never appear on touch. Replace title-only meaning with visible or ARIA text and add pressed/focus states. |
| Safe-area insets for notches and home indicator | S9, S10 | `env(safe-area-inset-*)` requires `viewport-fit=cover` to lay out edge-to-edge; without cover the browser insets the page automatically and the env() values resolve to 0. Insets can be non-zero on left/right in landscape. | SPA sets cover (`index.html:5`) and uses insets in the composer (`hutch-composer.css:100-105`), tall modal footer (`style.css:1762`) and phone root (`style.css:2041`). Server pages load that composer CSS (`base.html:26`) but their viewport meta has no `viewport-fit=cover` (`base.html:6`), so the composer's bottom inset is always 0 there. Marketing (`website/index.html:5`) also lacks cover while placing fixed/sticky elements (`website/styles.css:52,281,515`). Add cover per shell and test left/right insets. |
| Rage taps / missing touch feedback | S14, S15 | Rage clicks/taps are clusters of rapid repeated activations in one area, a strong frustration signal; dead clicks are activations with no visual feedback or navigation. | Hutch buttons give mostly a 1px `:active` translate (`app/src/input.css:244`); no pressed state exists for the icon rail, roster rows, or many menus, and long-press/selection feedback is absent. iOS also zooms focused fields below 16px, already mitigated (`style.css:1930-1934`). Treat missing press feedback as a defect class; the audit should sample controls with no state change on activation. |
| WCAG 2.2 target size and hit area | S12, S13, S15 | WCAG 2.2 AA 2.5.8 requires 24x24 CSS px (with a spacing exception); WCAG 2.5.5 (AAA) requires 44x44. The measured "target" is the hit area, so a small glyph can sit in a larger clickable box. | Hutch's own standard is 44px (`DESIGN.md:322-323`, `docs/design-system.md:100`) and 179 `44px` declarations back it. Gaps to audit: base `.icon-btn` is 32px, only 40px under `(pointer: coarse)` (`style.css:1800` vs `DESIGN.md:322-323`); server-page `.nav-toggle` is 38px (`hutch.css:328-329`); model pill is 36px tall (`studio.css:803`); marketing relies on one token (`website/tokens.css:101`). WCAG AA is met even by 32-40px; Hutch's own 44 standard is not consistently met. |
| Dashboard/SPA failure classes: fixed frame, two shells, sheet sizing | S7, S1 (incident class), repo | Fixed-height app frames with internal scroll are correct on mobile only if the frame tracks dynamic viewport changes and sheets/bars respect insets; otherwise bottom content disappears behind chrome. Dashboards also accumulate breakpoint drift when several stylesheets each own media queries. | The SPA app frame never page-scrolls by design (`DESIGN.md:304-305`): `.app-shell` is `100dvh` with a grid and internal scroll (`style.css:233-240`). Bottom sheets mix units: `93dvh`/`100dvh` modal cards (`style.css:1758-1759`), `100dvh` needs-you drawer (`style.css:1857`), `calc(100dvh - 136px)` action sheet (`studio.css:1014-1016`). Each is a place where toolbar/keyboard changes and insets can clip actions; the audit should enumerate sheets and bottom bars across both shells. |
| Static marketing site failure classes | S1, S17, repo | Marketing sites break in a different pattern: missing viewport meta (whole-site shrink), navigation collapsed to a mobile dialog, tables reflowed to cards, fixed/sticky decoration colliding with small viewports, and hover-only affordances. | The site has 17 media blocks spanning 640/760/900/940/1023px (`website/styles.css:46-539`) and a 1024px nav intent in `DESIGN.md:268-273` vs an actual 1023px rule (`website/styles.css:276`). Fixed skip link (`styles.css:52`), sticky FAQ intro (`styles.css:515`), drawer `max-height: calc(100dvh - ...)` and 44px token rows (`styles.css:280-297`), receipts table `min-width: 760px` with a card stack (`styles.css:341`). Marketing e2e runs Chromium without touch emulation and only at 1440/768/390 widths in the main guard (`tests/e2e/test_website.py:89-102`), so touch/landscape-phone regressions are invisible. |

## Existing responsive handling in the repo (inventory)

### Shells and viewport metadata
- SPA metadata: `src/hutch/server/static/index.html:5` - width=device-width, initial-scale=1, viewport-fit=cover. Loads `ui.css`/`style.css`/`studio.css` (lines 16-27).
- Server pages metadata: `src/hutch/server/templates/base.html:6` - width=device-width, initial-scale=1, no viewport-fit. Loads `hutch.css` and page/composer sheets (lines 14-30).
- Marketing metadata: `website/index.html:5` - width=device-width, initial-scale=1, no viewport-fit.

### Shell behavior and breakpoints
- SPA shell: `.app-shell` grid 272px + 1fr, `height: 100dvh` with `100vh` fallback (`src/hutch/server/static/style.css:233-240`); docked-collapse rules at min-width 901px (`style.css:380-408`); phone overlay sheet and single column at max-width 900px (`style.css:1680-1694`), coordinated in JS by `matchMedia("(max-width: 900px)")` with an inert/close handler (`app.js:2504,2542`).
- Server pages: no app shell; `body` is `min-height: 100vh` flex column (`hutch.css:57`); topbar wraps at <=720px (`hutch.css:302-317`); hamburger overlay nav appears below 1400px (`hutch.css:331-343`) with matching JS constant (`hutch.js:188`); grid collapses at 1100/1000/760 (`hutch.css:292-302`).
- Server page + SPA shared form/select/message tiers each carry their own media rules (e.g. `hutch-form-controls.css:172,225`, `hutch-select.css:99,262`, `hutch-messages.css:299,310`), so a control's phone behavior can differ by tier.
- SPA also uses 640px (36 uses) and 560px (10) as the dominant phone thresholds (`style.css` and `studio.css` throughout); `studio.css:776-797` adds short-window rules (max-height 760/520px) for first-run; `studio.css:1014-1016` caps the action sheet against `100dvh`.
- Brand surfaces carry their own responsive/coarse rules: `src/hutch/web/styles/hutch-surfaces.css:357,373`, `src/hutch/web/styles/hutch-bot-card.css:111,118`; Tailwind source adds the 1001px sidebar-width rule and two container queries (`app/src/input.css:39-43,55-63`) and phone stacks at 640/1100 (`app/src/input.css:149-177`).

### Pointer / hover / touch
- `(pointer: coarse)` is used deliberately in 30+ blocks (e.g. `style.css:1794-1813,1926-1929`, `studio.css:132,156,166,506,791,906,934,1012`). Only one hover-capability query: `@media (hover: hover) and (pointer: fine)` at `style.css:1850-1853`.
- JS reads `matchMedia("(pointer: coarse)")` for the Enter-to-send default (`app.js:4210`) and `(pointer: fine)` to focus search fields (`model-switcher.js:442`); no touchstart/touchend branching. One presentational platform sniff chooses the Cmd/Ctrl hint (`app.js:3636`); it does not gate behavior or layout.
- 151 bare `:hover` selectors across dashboard and marketing sources; most are cosmetic (background/border/color). No reviewed dashboard action is hover-only: the single hover-gated ruleset only raises roster-option contrast (`style.css:1850-1853`) while the base state stays tappable.

### Viewport units, insets, containers
- `100vh`: only `hutch.css:57` (server pages) and the `style.css:238` fallback. `dvh`: 19 uses (`style.css`, `studio.css`, `hutch-select.css:217`, `website/styles.css:283`). One `100svh` (`style.css:2041`).
- Safe-area `env()`: exactly 3 uses - `style.css:1762` (tall modal footer), `style.css:2041` (phone root top/bottom), `hutch-composer.css:104` (composer bottom on narrow layouts). No left/right inset handling.
- Container queries: `style.css:2182,2189,2194` (service tile, 16/18rem); `studio.css:687,767` (first-run 660/559px); `studio.css:914,917,965` (assistant settings 480/520-759/760px). The dashboard Tailwind source adds the two noted above (`app/src/input.css:55-63`); the marketing Tailwind source adds none.

### Target sizes
- 44px appears 179 times across sources: 97 in `style.css`, 20 in `studio.css`, 6 in `controls.css`, plus brand/marketing/Tailwind. `DESIGN.md:322-323` and `docs/design-system.md:100` state 44x44 as the phone standard; `docs/design-system.md:215,301` repeat 44px minimums.
- Known outliers: desktop `.icon-btn` 32px and coarse 40px (`app/src/input.css:254-255`, `style.css:1800`), server `.nav-toggle` 38px (`hutch.css:328-329`), `.ms-btn` 36px (`studio.css:803`), `.chip-del` 36px on coarse (`style.css:1801`).
- iOS zoom guard: coarse-pointer form fields get a 16px minimum (`style.css:1930-1934`; also `hutch.css:226`, `hutch-form-controls.css:248`).

### Stated requirements in design docs
- `DESIGN.md:283-284`: 304px sidebar above 1000px, 272px on smaller layouts; 380px context drawer fixed below 1100px.
- `DESIGN.md:304-311`: conversation column max 760px, composer pinned 24px above the safe area, feed scrolls internally (app frame never page-scrolls); first-run is pane-width responsive via container query at 660px; landscape phones go single-column; short windows compress.
- `DESIGN.md:322-323`: phone <=900px single surface + overlay nav; <=640px hides header meta; 44x44 touch targets.
- `DESIGN.md:367-370`: routine buttons >=40px, compact desktop 32px, coarse-pointer 44px; fields/selects 44px/16px text.
- `docs/marketing-site.md:318-324`: marketing measured at 1440x1000, 768x1024, 720x480, 360x844, 320x800; `docs/marketing-site.md:326` names the gap: no physical-device or screen-reader session.

### Automated coverage gaps
- Playwright is Chromium only; tablet cases are portrait heights at 900/768 widths (`tests/e2e/test_saved_requests.py:105-106`, `test_route_state_boundaries.py:31`, `test_computer_panel.py:116`, `test_dropdown_controls.py:59`). Phone cases are 390/360/320 wide, mostly without `has_touch` (`test_composer.py:334-335`, `test_website.py:89-102`).
- No viewport at 1366x1024, 1376x1032, 1024x768 landscape, 844x390 landscape phone, or iPad UA/touch combination (grep for "1366" under `tests/` returns nothing).
- A few WCAG/touch checks exist: 44px send button at phone sizes (`test_composer.py:345`), touch contexts in `test_wcag_fixes.py:89-90,201-202`, skip-link target size (`test_wcag_fixes.py:86-90`).

## What this changes in the plan

1. Add a first-class device matrix to e2e before any CSS edits: 1366x1024 (iPad Air 13/12.9 Pro), 1376x1032 (iPad Pro 13 M4), 1024x768 and 768x1024, 844x390 landscape phone, 390x844 phone, 1440x900 desktop - with `has_touch/is_mobile` for the iPad and phone cases, and 200% reflow at 720x480 kept.
2. Treat input capability as orthogonal to width: audit every hover reveal and `title=""`-only affordance; add `@media (hover: none)` or focus/pressed equivalents where hover is currently decorative-only for an action. Do not add UA checks.
3. Unify the viewport contract: add `viewport-fit=cover` to `base.html` and `website/index.html`; replace server-page `body` 100vh with `100svh` minimum; keep SPA `100dvh`; document one shell-height rule.
4. Inventory and fix bottom-sheet/bottom-bar safe-area usage across the SPA and both other surfaces (modal footers, needs-you drawer, composer, action sheets, marketing drawer) including left/right insets in landscape.
5. Run a target-size reconciliation: raise coarse icon buttons to 44 (`style.css:1800`), server nav toggle 38 -> 44 (`hutch.css:328`), model pill 36 -> 44 on coarse (`studio.css:803`), and verify hit boxes (not glyphs) meet the 44 standard; WCAG 2.5.8 AA already passes at 24.
6. Decide and test one navigation model per width: SPA overlay at <=900 vs server overlay at <=1400 is intentional or a bug, but a 1366 iPad must not get hamburger on technical pages and a full sidebar in the SPA in the same session. Align the threshold or document the split in DESIGN.md.
7. Only then touch breakpoints: prefer container queries for pane-owned layouts (service tiles and settings panes already prove the pattern), and remove duplicate media thresholds where the newer tiers already own the phone rules.
8. Add a keyboard/visual-viewport test or manual check for the composer and action sheets, and a marketing touch/landscape pass, because neither exists today.

## Unknowns / unverified

- No real iPad, iOS Safari, notch hardware, or split-view session was available; all conclusions about iPadOS behavior come from the cited sources plus source review. The e2e harness is Chromium, not WebKit, so Safari-specific fixes cannot be proven locally.
- The Apple Support guide used for Split View / resizable workspace behavior (S18) could not be machine-fetched (dynamic page); split-view/Stage Manager behavior is cited from that document's known scope, not from text this session read. Treat the exact resize steps as unverified.
- `any-hover`/`any-pointer` behavior for iPad + trackpad was not measured; the plan should test both primary-pointer states.
- Exact iPad Safari chrome heights in landscape, toolbar-collapse timing, and Home-indicator inset values on current iPadOS were not measured; only the unit mechanics were verified.
- No analytics or session-replay data (rage clicks/taps, dead clicks) exists in this repo, so real user frustration frequency is unknown; the rage-tap finding is a design risk, not a measured defect.
- Apple developer documentation pages (HIG layout/multitasking, Safari 15.4 release notes) render via JavaScript and could not be read as text; they are not cited as evidence here beyond the Can I Use support data.
- File:line citations are a snapshot of uncommitted working-tree state and will shift when the parked brand/dashboard work is committed.
- Cost/benefit of adding a WebKit (Playwright `webkit`) job is unestimated; the existing harness deliberately uses Chromium.
