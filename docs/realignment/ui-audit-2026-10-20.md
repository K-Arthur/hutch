# Hutch UX/UI audit and improvement (2026-10-20; evidence refreshed 2026-10-21)

## Scope and method

This review used the current `PRODUCT.md`, `DESIGN.md`, shared tokens, and the
current application and website source. Existing captures dated before this
review were treated as historical. The app was run with isolated temporary
state. The first-run capture had no assistants, runs, approvals, conversations,
or configured connections. Separate app-route captures used clearly synthetic
assistant/run fixtures (`mock/demo`); they made no provider calls. The public
site was checked for requests outside its own origin.

Chromium 153 / Playwright 1.63 captures cover 1440×960, 900×1024, 390×844,
and 320×740 CSS pixels. The Past Work keyboard check also used a 320×420 short
viewport. Rendered screenshots were opened and inspected individually; the
contact sheet was not used as the visual review. Browser assertions checked
document and table overflow, accessible labels, target dimensions, focus
behavior, empty states, long names/content, search, filters, paging, and
recoverable failure states where the existing WCAG suite covers them.

## Findings and changes

| Priority | Evidence and affected task | Cause and impact | Change and measurable check |
|---|---|---|---|
| P2 — fixed | Past Work search only covered the first 200 locally loaded runs. With more history, finding an older task or assistant required scanning a capped list. | The page fetched one capped list and filtered it in the browser, while the existing API/store already supported offset paging. | Added literal, case-insensitive substring search over task prompt, assistant slug, and display name, then connected the page to 50-record API windows and 25-card reveal steps. A 225-run fixture finds the oldest marker, respects filters, loads successive pages without duplicates, and keeps the keyboard-operable control available at 320×420. No provider calls. |
| P2 — fixed | Landing-page availability information was difficult to scan on a narrow phone: status was separated into a wide table column and the “Experimental” label hid important limits among many capabilities. | The table depended on a wide three-column layout and its responsive treatment removed status detail on narrow screens. | Recast it as two columns, with each row naming one area and keeping its status beside that name. Split provider, account-scope, approval, and verification limits into separately labeled rows. Browser checks report zero page overflow at 1440, 900, 390, and 320px, zero table overflow, and no off-origin requests. |
| P2 — fixed | The pointer-reactive hero fetched all 21 animation frames as soon as the page became idle. It also downloaded the same font twice because the preload and CSS URLs differed. A fresh 1440×900 run measured 1,225,715 encoded bytes before interaction, above the 900KiB transfer budget. | Idle preloading made optional pointer art part of initial page transfer; the font cache keys prevented reuse. | The page now loads only the frame needed for the pointer position and reuses the preloaded font URL. A repeated 1440×900 run loaded one font and at most two needed frames before deliberate interaction, measured 366,508 encoded bytes (including the minified custom stylesheet), and confirmed another frame loads after pointer movement. |
| P3 — fixed | “The questions people actually ask…” suggested direct user research that the preview does not document. | Copy implied evidence that was not available. | Replaced it with neutral “Questions about what an assistant can do…” wording; confirmed the phrase in source and current landing-page captures. |
| P2 — evidence corrected | The document called the 2026-10-08 marketing screenshot current even though its source hash was stale and its hero showed retired copy. | Audit records treated a dated capture as current evidence. | Marked that capture historical in `docs/marketing-site.md` and `docs/realignment/visual-validation.md`; linked the current source-pinned evidence below. |

Before/after checks: on the 225-run fixture, the old 200-item browser list could
not reach the oldest record; the revised search returns that task directly and
the paging control traverses beyond the first 200. At 320px, the earlier
availability table measured 285px of content in a 254px viewport; the current
two-column table measures 254px in the same space. Whole-page overflow is zero
at all four widths.

The stale capture did not establish a defect in the current landing page; it was
a documentation and review-evidence defect. Current marketing capability
claims were checked against the support matrix and retained with their
preview, approval, OAuth-scope, and verification limits visible.

## Remaining verification limits

No direct user sessions, physical-device checks, live-provider/OAuth checks, or
screen-reader session were available. The browser environment has no installed
axe-core runner, so this review does not claim a complete automated WCAG 2.2
AA audit. The short 320×420 viewport is a keyboard-navigation stress check; it
does not reproduce a mobile operating system's on-screen keyboard. Forced
colors were checked in Chromium at phone width; text resizing and all
browser/OS combinations were not certified. Transfer sizes were recorded from
an uncompressed local static server; deployment gzip/Brotli behavior was not
measured. The current compiled framework CSS file is 51,665 encoded bytes locally;
the editable Hutch-specific stylesheet is 42,310 bytes and its served minified
asset is 35,588 bytes, within the 40KiB custom CSS transfer budget. Legacy `/legacy/runs` is
confirmed to return a titled, language-tagged 404; other retired legacy URLs
were not exhaustively enumerated. The current screenshots and tests provide
repeatable evidence for the reviewed surfaces, not a substitute for assistive
technology or user testing.

## Chat recovery and settings follow-up (2026-10-21)

The recent-chat selector loaded at most 100 conversations. Directly opening an
older selected conversation therefore substituted a different recent chat. The
application now preserves the requested conversation ID, fetches it outside the
recent window, and exposes a paginated title library for active, archived, and
imported history. A focused browser fixture creates 106 conversations, opens
the oldest direct link exactly, filters it through the library, and checks the
new Chat library and Settings at desktop and 390px phone widths without
horizontal overflow.

Workspace model defaults and the optional motion override moved from a compact
footer popover to Settings. The page states that defaults affect only newly
created assistants; existing assistants and chats retain their choices. The
same focused browser check saves reduce-effects and restores the system setting.

Assistant settings now use one 760px reading column for everyday edits and the
customization disclosure. The former 760px/1056px pair made semantic peers
appear unrelated. The follow-up keeps deeper controls available without adding
another navigation layer or hiding a required setting.

## Guidance consulted

- [WCAG 2.2 Understanding](https://www.w3.org/WAI/WCAG22/Understanding/)
  and [W3C page structure tutorial](https://www.w3.org/WAI/tutorials/page-structure/)
  informed reflow, focus, target, and landmark checks.
- [W3C reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
  informed the 320px and 390px no-horizontal-overflow assertions.
- [GOV.UK details guidance](https://design-system.service.gov.uk/components/details/)
  informed the labeled assistant-settings disclosure: its summary describes the
  controls it reveals instead of concealing a required everyday edit.
- NN/g guidance on [recognition over recall](https://www.nngroup.com/articles/recognition-and-recall/)
  and [progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
  informed labeled status and visible-on-demand detail.
- Open WebUI [mobile history](https://github.com/open-webui/open-webui/issues/27241)
  and [iOS focus](https://github.com/open-webui/open-webui/issues/31372)
  issues were treated as individual risk scenarios to test, not prevalence
  claims or design templates.
