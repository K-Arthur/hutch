# Requirements (v0.2) and implementation status

Source: *Hutch requirements v0.2 draft*, 7 Oct 2026 (UI = dashboard, LM = local models,
CO = collaboration, SR = safety and reliability, PF = performance). IDs are stable so issues and
commits can cite them. Evidence for the *why* is in
[research/offerings-and-failures.md](research/offerings-and-failures.md) and the
[Grok Bot product review](research/grok-bot-product-review-2026-10-09.md).

**Status key:** `done` — implemented and covered by a test or a recorded measurement ·
`partial` — implemented with a stated gap · `later` — scheduled after v0.1 per the draft ·
`planned` — not yet built.

> Performance numbers in the draft are *proposed targets*. Measured values live in
> [performance.md](performance.md) and the committed `benchmarks/baseline.json`.

*Status column last updated: 2026-10-10. Studio New Bot carries the latest user message into an editable, provenance-linked draft; each visible user message also offers **Make a bot**, which seeds setup from that exact request rather than requiring it to be restated. The owner may select up to eight earlier user messages from the same chat as reviewed saved background; later messages, assistant replies and other chats stay excluded. Setup suggests an editable professional Bot name and stable address locally. When a validated workspace or source-chat model route is available, a one-screen quick path uses that route with managed workspace, no tools, ask-first actions and no schedule defaults; **Customize** preserves the full model/tools/memory/workspace/schedule/limits/import/review flow. Without a configured model, setup requires an explicit route selection and never falls back silently. From the workspace coordinator chat, the owner may request a tool-free draft of standing instructions using the exact source request, current editable purpose and explicitly selected earlier user messages. The coordinator can ask up to five material follow-up questions one at a time, with 2–5 choices plus free text; the same browser restores each question, prior answers and unsent answer for up to seven days. The response is a suggestion only; the owner edits/applies it and still reviews the Bot setup. Drafting uses normal run admission and budget controls, creates no Bot and changes no authority. It lists material unknowns rather than guessing. A two-round browser journey verifies exact source provenance and reload restoration; live model quality remains unverified. A named workspace coordinator now offers one user-reviewed handoff to an approved specialist with a separate chat and durable parent status/result card; schema v41 adds an empty-by-default specialist allowlist enforced at task admission, and users can attach one exact specialist response to a coordinator follow-up. Schema v31 records content-free committed-event checkpoint markers and schema v32 adds optional task-only snapshots of reviewed coordinator facts. Schema v34 supports one narrowly gated, owner-confirmed fresh run from a failed/stopped built-in task checkpoint with no recorded action or child work and unchanged permissions; it does not resume processes, carry prior tools/receipts/facts or continue `outcome_unknown`. Schema v35 adds isolated Outlook Mail read credentials and Bot grants; schema v46 adds a separate Outlook send-only grant and an experimental **Connections setup** for it, with exact per-message approval and no ambiguous-result retry. Schema v47 adds a separate Gmail send-only grant and an experimental **Connections setup** using sensitive `gmail.send`; each plain-text message needs fresh exact approval and an ambiguous result is never retried. Generalized result delivery and broader team planning remain open. Built-in conversational runs support durable typed choices; external runtime coverage and final release validation remain open. Google Calendar and Outlook Calendar reads, plus separately permissioned Outlook Mail search previews, are implemented behind OAuth and Linux Secret Service setup; live account and consent verification remains outstanding. Calendar and Gmail share a public Google Desktop OAuth client ID that an owner can save locally in Connections or an operator can provide through an authoritative environment override. Gmail search remains an experimental private preview requiring restricted `gmail.readonly`, Linux Secret Service, and loopback-only Local Bot routes. A separate send-only account requests sensitive `gmail.send`, allows one approved plain-text email at a time, and cannot read the mailbox; the sender address is entered during setup. No live account was tested, and public availability remains blocked on applicable Google OAuth verification. The restricted-scope security assessment applies to mailbox-read data, not the send-only scope. Protected browser credential entry and human checkpoints are partial and still need headed/live verification. Schema v38 adds explicit, durable and revocable sharing of an exact reviewed memory fact with one named Bot; Bot settings now offer a bounded plaintext JSON export of every revision, review decision, provenance record and explicit share snapshot. Permanent deletion remains unavailable, and broader memory-policy journeys and broad restart recovery remain incomplete. Schema v39 adds a reviewed, owner-launched OpenCode CLI coding handoff in an isolated worktree, without transferring Hutch budget, command approval or sandbox guarantees.*

The OpenCode coding handoff now includes `hutch code login`, which uses the installed CLI's supported interactive provider flow and stores the connection in a private profile under Hutch state. The task runner checks that profile before claiming work and uses its persistent `OPENCODE_DB`; it does not import the regular OpenCode profile. Fixture coverage and a no-account CLI status check passed. No real provider sign-in, model call, or provider billing was exercised; usage remains outside Hutch's budgets.

### Owner-requested conversation and personal-account features (2026-10-09)

These requirements were added after the original realignment plan. They are product scope, not claims
about current behavior. The first delivery order is typed chat choices, a staged chat-led bot draft,
then account integrations. The order keeps user experience work testable before adding long-lived
third-party authority.

For integrations, Hutch must show which account and operation a bot can use, keep credentials out
of prompts/transcripts and the SQLite database, scope access per bot, and revoke it from Connections.
Every external write is a fresh immutable approval containing the account, destination, exact
payload, and expiry; a conversation choice never grants that authority. OAuth must use an explicit
user-delegated flow suitable for a local app. The provider's current scope and review requirements
must be checked before implementation: [Google Calendar scopes](https://developers.google.com/workspace/calendar/api/auth),
[Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes),
[Microsoft Graph permissions](https://learn.microsoft.com/en-us/graph/permissions-reference), and
[Microsoft authorization-code/PKCE guidance](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).
Gmail message-body access is a material release dependency because Google's current documentation
classifies the relevant read scopes as restricted and describes verification/security-assessment
requirements.
