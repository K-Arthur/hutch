# Reliable memory across Hutch agents

**Hutch needs a runtime-independent authority for history, memory and task continuity—and already has the essential SQLite foundation.** It stores conversations, reviewed facts, execution events and receipts; replacing these with another memory database would introduce competing authority. The necessary investment is consistent context delivery, recoverable session bindings, bounded retrieval and durable ordinary-chat commitments. Own persistent state is essential; always-shared cross-bot memory is not. Grok Bot and Meta Muse support the distinction between durable continuity and indiscriminate sharing, but their documentation does not prove equivalent reliability, security or speed. Implement the five backend slices below, starting with A1, while preserving human review, explicit sharing and honest uncertainty about external effects.

This synthesis uses four completed notes dated **2026-10-23**: [product references](../research_notes/Reliable%20memory%20across%20Hutch%20agents/product-references.md), [assistant applications](../research_notes/Reliable%20memory%20across%20Hutch%20agents/assistant-applications.md), [memory frameworks](../research_notes/Reliable%20memory%20across%20Hutch%20agents/memory-frameworks.md), and [Hutch’s current-state audit](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md). Product evidence is verified documentation, **not hands-on behavior**. Code findings are static inspection at `main@f29b299b58b865053d48f4baa71601e191edb5cd`; tests were read, not run. No new web research or implementation occurred for this report.

## Grok and Muse support continuity without universal sharing

Grok’s October 22 v0.75.2 release documents that what a **personal Bot saves to memory in one chat is remembered across that person’s chats with the same Bot**. This is maintained memory, not evidence that every message is replayed. Team Bots distinguish private chats and person-specific notes from selected team facts: a fact enters team memory when someone explicitly says the team should have it, and the Bot announces the save. That trigger is not Hutch’s owner-review transaction, so the useful lesson is selective disclosure, not copying the approval policy. Separate Bot conversations also do not isolate the shared computer, files, credentials or browser state. ([Grok release](https://x.ai/changelog/bot#v0.75.2), [Team memory](https://docs.x.ai/grok-bot/team-bots#memory), [computer boundaries](https://docs.x.ai/grok-bot/computer-and-apps))

Grok’s documented handoff-result and Stop fixes show why retaining a conversation, finishing work and delivering its result need separate contracts. Reconnection after updates does not disclose transaction boundaries, effect deduplication or precise replay behavior. Its deletion release claims also coexist with retention qualifications and surviving shared-computer state. These are vendor statements, not independent crash, security or erasure tests. Hutch should adopt explicit ownership and cancellation evidence without promising cloud-style execution while its local host is stopped. ([Changelog](https://x.ai/changelog/bot), [recovery](https://docs.x.ai/grok-bot/troubleshooting), [privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy))

Meta officially identifies Muse as its personal agent. It documents awareness across main and side chats, inspectable/editable file-based memory, and Library artifacts. **Inspectable files are not its entire persistence architecture**: Meta’s launch engineering account separately describes durable application state in PostgreSQL outside the runtime cell and credential store. Side chats organize conversation; they are not documented privacy boundaries. Deleting a message, side chat or file can leave learned information intact; the forget skill operates “to the best of its ability,” while reset is a different destructive operation. Peter James’s export article reports reconciliation, indexes and memory consolidation, but its underlying archive was unpublished; it cannot establish proprietary internals or override Meta’s forgetting limits. ([Meta announcement](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/), [chat behavior](https://www.meta.com/help/superintelligence/1331373868832401/), [architecture](https://security.muse.ai/), [data controls](https://www.meta.com/help/superintelligence/2225571704857152/), [secondary export report](https://mouse.dev/blog/muse-runtime-export/))

## Comparable systems separate evidence, retrieval and execution

OpenClaw’s inspected development snapshot uses **per-agent SQLite transcript storage**, with older JSONL/session files retained for migration or archive. Its compaction stores a summary and retained-history boundary; memory files and their retrieval indexes serve another purpose. Source lineage helps exclude forgotten material from re-ingestion, but cannot erase arbitrary copies. Its separately tracked child-result delivery is especially relevant: execution completion does not prove parent receipt. Hutch should borrow explicit source boundaries and delivery identities, not OpenClaw’s automatic memory promotion or shared-workspace assumptions. ([Pinned storage specification](https://github.com/openclaw/openclaw/blob/42d41566c49cfccc727d5a0cd7aae1d5c4f428bf/docs/reference/session-management-compaction/store.md), [memory provenance](https://docs.openclaw.ai/concepts/memory-provenance), [result delivery](https://docs.openclaw.ai/tools/subagents/announce))

LibreChat separates durable MongoDB messages from transient streaming state, rejects incomplete summary checkpoints, and offers explicit user-plus-agent memory partitions. Its structured notepad is not semantic search over the whole archive. Open WebUI likewise retains account-owned chats separately from request compaction; its memory records and vector entries need coordinated lifecycle handling. Its account-level memory scope would not satisfy Hutch’s per-bot contract unchanged. Both illustrate why reconnectable streams or background tasks do not establish executor survival after process loss. **Open WebUI is source-available under a custom license, not unrestricted OSS**; exact snapshots and licensing are recorded in the application note. ([LibreChat checkpoints](https://github.com/LibreChat-AI/LibreChat/blob/94ae8a419839f8c99f5cfc15a650804ced8163c2/packages/api/src/agents/compaction.ts#L49-L136), [memory controls](https://www.librechat.ai/docs/features/memory), [Open WebUI memory](https://docs.openwebui.com/features/chat-conversations/memory/), [license](https://github.com/open-webui/open-webui/blob/91ea4e3421d1d8069f13d4a463fcb5986d94ea60/LICENSE))

Current Letta centers its harness and **MemFS**, an agent-owned Git memory repository with bounded always-visible files and on-demand directories. Its retired V1 block APIs are not the recommended implementation model. Git history supports inspection and conflict handling, not truth or authorization. LangGraph makes another useful separation: a thread checkpointer retains execution state, while a cross-thread Store holds knowledge. Namespace tuples do not grant access, and replay can repeat an effect whose remote success preceded local recording. Adopt these distinctions inside Hutch; do not add another harness. Defer Graphiti, embeddings and extra services until labeled retrieval failures demonstrate a need beyond existing FTS5. ([Letta migration](https://github.com/letta-ai/letta/blob/8816d3a8516893bfdc0fa14bfb1235226012e295/README.md), [MemFS](https://docs.letta.com/concepts/memfs/index.md), [LangGraph checkpoints](https://docs.langchain.com/oss/python/langgraph/checkpointers), [idempotency](https://docs.langchain.com/oss/python/langgraph/functional-api#idempotency), [framework evidence](../research_notes/Reliable%20memory%20across%20Hutch%20agents/memory-frameworks.md))

## Hutch’s gap is consistent delivery, not absent storage

Hutch already transactionally admits messages, tasks, runs, context snapshots and retry receipts. SQLite events underpin recoverable transcript mirrors, fenced writes and assistant-message projection. Facts have immutable revisions, hash-bound review, scoped FTS5 retrieval and explicit sharing. These are substantial existing guarantees to preserve, not rebuild. Builtin uses the admission context, currently bounded to the newest **12 messages and 16,000 characters**; within-run compaction cannot recover obligations excluded before it starts. Its stored summaries are not ordinary next-run durable task continuity. ([Current audit](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md), [Store](../src/hutch/store.py), [memory contract](../docs/adr/0008-memory-and-bounded-collaboration.md))

The OpenCode adapter exposes a concrete mismatch. It ignores `run.conversation_context`, including selected facts, reply references and specialist-result attachments, and discards Hutch Tool objects. A new native session reads an ascending **first 60-message page**, then selects a suffix of that old page. It removes the current user input by text matching rather than message identity. Existing sessions receive only the current prompt; reuse checks route/session existence without a synchronization cursor, so OpenCode → Builtin → the same OpenCode route can omit intervening turns. **These are static control-flow findings, not newly reproduced live bugs.** ([Audited adapter](../src/hutch/runtime/opencode.py), [audit evidence and limitations](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md))

Partial-state fidelity also needs repair: events can retain output marked incomplete, while assistant-message projection drops its incomplete/reason metadata. Later context can therefore present qualified partial text as ordinary output. Conversely, Hutch does have recovery machinery: parked same-bot delegation preserves model state under validated continuation conditions; workflow instances retain node results; named tasks have a narrow owner-confirmed no-effect fresh-attempt path. None is arbitrary ordinary-chat loop recovery, but claiming “no recovery exists” would be wrong. ([Projection and continuation audit](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md), [receipt execution](../src/hutch/runtime/steps.py))

Memory improvements must not obscure external-runtime limits. OpenCode’s native tools execute with the user’s OS authority, outside Builtin containment, and do not traverse Hutch’s ordinary effect-receipt bracket. Existing approval, per-generation budget and accounting gaps remain separately unresolved. Run-bound retrieval authorization cannot sandbox native file access or make every tool action freshly approved, budgeted or exactly once. ([External-runtime decision](../docs/adr/0007-external-runtimes.md), [adapter-limit audit](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md))

## Implement A1–A5 through the existing authority

**A1—One provenance-aware bounded context contract comes first.** Extend the existing admission snapshot and projection paths so both adapters consume the same authorized selection. Carry message/reference IDs, scope, exact revision/hash, source ranges/high-watermarks, and incomplete/truncated status where applicable. Select recent history from canonical ordering; deduplicate current input by identity, never string equality. Preserve selected fact, reply, artifact and specialist references. Keep originals when compaction fails; a derived context manifest describes what was selected without becoming a second transcript authority. ([Admission seams](../src/hutch/store.py), [compaction policy](../docs/adr/0019-cost-guardrails-context-continuity-and-routing.md))

**A2—Persist native-session bindings and reconcile delivery.** Treat native sessions as replaceable execution caches. Bind them to bot, conversation, route, workspace and policy/instruction revision, with durable synchronized-message identity and submission state. Reconcile gaps or rebuild from Hutch’s admissible snapshot when mappings disappear, sessions are deleted or routes change. Ambiguous prompt acceptance must remain uncertain until reconciled; do not blindly resend a potentially accepted operation or release uncertainty as if rejection were proved. Prefer existing admission/receipt paths, adding migrations only when existing authority cannot represent required state. This does not promise provider-side exactly-once delivery. ([Current session/submission path](../src/hutch/runtime/opencode.py), [honest outcomes](../docs/adr/0003-durable-state-and-honest-outcomes.md))

**A3—Expose supported, run-bound memory/history access.** Use the existing Hutch operations for Builtin and a verified OpenCode V2 bridge. The new session must load the OpenCode skill and consult relevant current API documentation before selecting that bridge. Bind bot/conversation/run/fence server-side, never through model-chosen authority; expose no broad database or administrative access. Recheck cancellation, lease/fence, applicable memory-off state and grants at every retrieval/call. Facts remain untrusted reference data, never system instructions. Retain tool-free modes and same-bot child exclusions. If the bridge is genuinely unsupported, report A3 incomplete with the exact blocker—no fake tools or parity claims. ([Memory operations](../src/hutch/tools/memory.py), [scope enforcement](../src/hutch/fact_memory.py), [integration authority](../docs/adr/0017-governed-mcp-integration-plane-and-context-scaffolding.md))

**A4—Persist ordinary-chat task continuity and retrieve older evidence selectively.** Store versioned goals, constraints, decisions, pending questions and artifact references, anchored to canonical messages with revision checks and explicit supersession. Record observable commitments, decisions and results, never private chain-of-thought. Keep pending work distinct from receipt-backed completion. Add bounded, scoped historical retrieval using existing message search; distinguish “what was said” from current reviewed facts. Evaluate FTS5 selection and ranking before changing infrastructure. Summaries remain lossy, derived and untrusted: they cannot grant permission, certify effects or silently promote transcript claims. ([History and task-state gaps](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md), [retrieval candidates](../research_notes/Reliable%20memory%20across%20Hutch%20agents/memory-frameworks.md))

**A5—Close recovery, sharing and delivery evidence, then document the limits.** Preserve human review for every recallable proposal, explicit bot-wide promotion and exact-revision cross-bot grants. A newer unreviewed revision must retain the current suppression behavior rather than inherit old approval. No global writable memory, transcript pooling or automatic workspace sharing is justified. Frozen task snapshots remain frozen evidence, distinct from reusable revocable grants. Revocation stops future authorized retrieval; when future native contexts would reuse revoked grant material, invalidate the binding and rebuild an admissible context. Previously disclosed text and provider copies cannot be recalled retroactively. Archive is not permanent erasure. ([Fact rules](../docs/adr/0008-memory-and-bounded-collaboration.md), [delegation and grants](../docs/realignment/delegation.md))

## Acceptance must cover omitted context and uncertain outcomes

Run one vertical slice at a time, but finish all agreed acceptance IDs. The following matrix defines completion; it is **proposed evidence, not executed results**. It derives from the [code audit](../research_notes/Reliable%20memory%20across%20Hutch%20agents/hutch-current-state.md) and [framework evaluation note](../research_notes/Reliable%20memory%20across%20Hutch%20agents/memory-frameworks.md).

| ID | Required acceptance evidence |
|---|---|
| **A1** | More than 60 messages retain the latest correction; identical user strings with distinct IDs each arrive once. Selected fact/reply/artifact/specialist references survive reconstruction. Incomplete, empty and truncated output remain distinguishable; unrelated chats never enter context. |
| **A2** | OpenCode → Builtin → OpenCode and route A → B → A reconcile correctly; missing/corrupt bindings and deleted native sessions rebuild safely. Restarts before acceptance and after dispatch/before acknowledgement preserve submission identity and uncertainty; no blind retransmission of uncertain non-idempotent effects. |
| **A3** | Memory-off, no-grant Bot B probes, source updates/revocation, cancelled runs, stale leases/fences, concurrent review/edit and hostile fact text respect current authority. Proposals stay unrecallable until exact-revision review. Cached contexts follow the disclosed revocation boundary. |
| **A4** | Obligations and corrections older than 12 turns remain retrievable with provenance. Repeated compaction, smaller/unknown windows, failed/nonshrinking summaries and failed checkpoint writes preserve originals and explicit limitations, not fabricated completion. |
| **A5** | Restart after result commit/before parent consumption yields one logical delivery without re-execution. Old child replies never resume cancelled parents; same-bot children receive no reference memory, specialists only selected snapshots. Stale workers cannot project results; existing histories, receipts and user bots survive upgrades. |

Use deterministic adapter assertions and isolated process-failure fixtures to prove selection, ownership and delivery behavior. Separately evaluate live-model response quality only with authorized credentials; those credentials and live evidence were unavailable to this research. Compare the same corpus, routes, budgets and hardware against the same baseline: prompt tokens, p50/p95 selection latency, labeled retrieval correctness, provenance resolution, stale results and unauthorized disclosures. Record denominators and failures; do not invent a numerical performance target or equate retrieval success with answer correctness. Include database/index growth in storage accounting. ([Evaluation basis](../research_notes/Reliable%20memory%20across%20Hutch%20agents/memory-frameworks.md))

SQLite process-crash evidence is not power-loss certification. An outbox makes delivery obligations durable, not arbitrary network effects universally exactly once. Where remote success cannot be reconciled, honest uncertainty is the correct result. Storage alone cannot prevent hallucinations. ([Durability boundary](../docs/adr/0003-durable-state-and-honest-outcomes.md), [replay limitations](https://docs.langchain.com/oss/python/langgraph/functional-api#idempotency))

## Conclusion

Hutch can make changing runtimes less disruptive by making continuity independently inspectable: what context was selected, under whose authority, from which revision, and with what unresolved outcome. That creates a testable product contract instead of relying on a model’s apparent recollection. The [standalone new-session implementation prompt](Hutch%20memory%20implementation%20prompt.md) carries the full backend assignment. No additional comparative research is needed to begin; revalidate checkout drift and relevant OpenCode APIs, then implement A1 and continue through A5.
