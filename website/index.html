Keep each task reviewable from request to result.

A bot keeps its instructions and limits. Chat and named recurring tasks start real runs; proposed actions stay reviewable, and the run record remains available after completion.

  1. 01

    Give a bot a task

    In Studio, choose Make a bot under the request you want to reuse, or select New to start from your latest request. Hutch locally suggests an editable teammate name, clear work role and stable local address without an extra model request; the Bot or workspace model route is suggested when available, and Studio keeps the AI Bot label visible. Only that selected request and earlier user messages you select become saved background; later messages, assistant replies and other chats stay excluded. The display name and address stay editable. New Bots use a managed workspace, no tools, ask-first actions and no schedule. Review optional starters, tools, limits, recurring work or human browser handoff before saving. Creating a Bot does not start a run.

    Experimental (built-in coordinator only): request a tool-free purpose rewrite from the exact source; each request returns one response. Select earlier user messages if useful. Edit and apply the draft yourself; it lists unknowns rather than guessing. Drafting creates no Bot or permission changes. Normal route and fallback limits still apply; hosted providers may retain the text, and live quality is unverified.

  2. 02

    Review the request

    The built-in chat can ask you to choose among options when it needs a preference. Your answer continues the conversation and never approves an action. Review an approval in chat or Needs you; allow once or deny. Unanswered requests expire to denial.

    Experimental coordinator handoff: review the selected specialist and saved settings, refine the goal and optional deliverable or constraints, then confirm. The coordinator chat keeps the original request, task, response and content-free progress timeline together.

    Continue only from a safe checkpoint: the failed or stopped built-in attempt has no recorded action or child work, and no later specialist work, pending question or uncertain effect; the coordinator chat and specialist settings must remain active and unchanged. Hutch starts a fresh run from the reviewed brief, constraints and committed response; it never resumes the old worker or replays actions. External runtimes stay blocked, and a new model call may use more quota.

    Attach only the exact specialist reply you choose, as untrusted text; other chat history, files and permissions stay separate. You may also select up to eight current, approved coordinator facts for that task alone. They are not specialist memory; providers may retain submitted copies. The specialist's own memory and workspace may apply. Live provider execution is unverified.

  3. 03

    Check the run evidence

    Inspect the final status, tool results, ordered transcript and reported usage. Uncertain effects remain visible for reconciliation. Keep memory private by default. If another Bot needs a fact, share the reviewed snapshot with that named Bot. Either side can revoke; the share adds no tools, account access or workspace context.

Keep control on your machine and choose the model each bot uses.

Hutch keeps control state on the host. Local sends prompts to your selected local model service; configured tools can still use the network. Hybrid lets each bot use a local or hosted route, with no silent paid fallback. Strict Offline is an experimental Linux mode that requires host-verified isolation and permits only its configured local model connection. Browser egress for HTTP(S) and WebSocket traffic uses a DNS-pinning proxy in local fixtures; public destinations and non-HTTP browser protocols remain unverified.

Inference

Hutch supports configured OpenAI, Anthropic, OpenAI-compatible and Ollama routes. In Studio, choose a route for the next message or select Save as Bot default for future chats and scheduled runs. Compatibility depends on the provider and endpoint version; live provider checks have not been performed for this preview.

Execution

Runs are supervised on Linux. Bubblewrap isolation is a Linux namespace sandbox, not a virtual machine, and must be enabled by the operator. Migrated bots may remain unsandboxed.

State

SQLite, transcripts and file-share records stay in ~/.local/state/hutch. Workspaces start fresh per run; choose a managed folder for one bot or a validated user folder. Chat Files lists verified downloads. The owner can add a revocable reference to another selected chat; bytes stay with the source run, outside the target workspace and model context. Shell-created files are not attached automatically. Managed folders survive bot deletion and sit outside database snapshots; back up those files separately.

Scheduling

One elected local supervisor runs schedules. The host must be awake and the service running; sleep and disconnection are visible limits.

Remote

The responsive dashboard supports experimental HTTPS-paired sessions. A person can take over the same visible Linux browser to enter passwords and one-time codes or complete CAPTCHA; Hutch does not type secrets or solve challenges. Resume checks the live page without reloading it. Phone browser handoff is unavailable.

Plans & keys

OpenCode Go uses its issued API key, copied into Hutch after you sign in there. Sign in with ChatGPT is an opt-in local preview; eligibility for Hutch is unconfirmed and scheduled use requires a separate permission for each Bot and account.

The honest limits

5 boundaries
  • Isolation has a boundary. Linux bubblewrap mode uses namespaces and resource limits; it is not a VM. It must be enabled, and migrated bots remain unsandboxed until an operator changes the setting.
  • Humans still review consequential actions. Prompt injection can produce harmful requests; approvals and denials reduce risk but cannot make an allowed action safe.
  • Usage amounts are estimates. Hutch reserves estimated tokens and priced cost before a hosted call. The provider controls actual tokenization and billing.
  • OpenCode coding tasks are experimental. A reviewed task can open the user's local OpenCode CLI in a pinned worktree. Its command approvals, account usage and shell authority remain outside Hutch's sandbox. OpenCode and Pi are unavailable as Hutch-managed Bot runtimes.
  • Phone supervision is not remote access. The phone dashboard supports experimental paired control, but cannot take over the browser. On Linux desktop, a person can enter passwords, codes and CAPTCHA responses in the same visible browser; Hutch never types credentials or bypasses challenges.
  • Delegation has a narrow boundary. The optional child-task tool requires a supervised Strict Offline Linux run and a fresh approval for every request. Children receive only the task text, run one at a time under the default two-run limit, and do not copy files into the parent workspace.

What usually stops people

The questions people actually ask before trusting an agent with their machine.

Do I need an API key, a credit card, or a GPU?

Hutch does not include hosted inference. Connect a compatible hosted provider or use a local model service that you already run; available models vary, and live paid-provider checks have not been performed for this preview.

What actually leaves my machine?

Hutch stores its control state locally. A hosted model receives the prompt and context Hutch sends to it; network tools connect to their own destinations. A local model can still use online tools. Review the selected connection and tools before running a task.

What happens when my laptop sleeps on a schedule?

Nothing runs while the machine is off. With the local supervisor running again, configured schedules detect missed windows and either coalesce them into one catch-up run or record a skip, according to the bot’s policy.

Can I hand coding work to OpenCode?

An experimental Linux handoff can prepare a reviewed coding task from a completed Hutch chat answer. You launch the installed OpenCode CLI from a terminal; Hutch creates a separate worktree from the reviewed Git commit. OpenCode uses its own sign-in, model and usage pool. Its shell approvals are not brokered or sandboxed by Hutch, so approved commands run with your Linux user's authority. The task branch stays separate for your review. This does not make OpenCode a Hutch-managed Bot runtime.

Can I run it on my ChatGPT or Claude subscription?

OpenCode Go connects through its provider API key: sign in with OpenCode, copy the key, and add it to Hutch. A separate experimental coding handoff starts the OpenCode CLI with its own sign-in, model and usage allowance; OpenCode's command approvals are outside Hutch's sandbox. Hutch does not reuse OpenCode's private sign-in file. Sign in with ChatGPT is an opt-in local-app preview; eligibility for Hutch is unconfirmed and its Responses API does not enforce Hutch's output-token allowance. Scheduled or coordinator-assigned work needs your express permission for each Bot and connected account; the permission follows that Bot's current provider routes and can be revoked. Hutch never reuses consumer-app cookies or sessions, and no plan is silently upgraded or selected as a fallback.

What does a runaway bot cost me?

Hutch estimates tokens and priced cost, reserves those estimates before calls, and stops admitting more calls when configured limits would be crossed. The estimate can differ from the provider’s invoice; use the provider’s own billing controls for an external spending limit. Uncertain calls remain held until reconciled.

Is it safe to let an agent touch my files?

Bubblewrap isolation is available only on Linux and must be enabled; it is not a virtual machine. Approval policy and transcripts provide operator control but do not guarantee safe decisions. Legacy bots may still have isolation disabled. Read the support boundaries above before use.
