# OpenBot MVP — Local-First Multi-Bot Agent Platform

## 1. Research conclusions (what changed vs. the original doc)

The original doc recommended OpenCode as the core harness + Python orchestrator. My research (Pi/OpenCode deep-dive, orchestrator landscape, 40+ cited user complaints) revises this:

- **Own the agent loop; make runtimes pluggable.** OpenCode's server is scoped to one project dir (N bots = N servers/ports), its Python SDK is alpha, and its API has no stability promise. Pi's RPC-over-stdio mode (one process per bot, documented Python pattern, MIT, very active) is the better *external* runtime. But the differentiating work — scheduling, approvals, budgets, isolation, transcripts — is plumbing **no framework provides** (evidence: "Build Your Own Coding Agent" ~500 lines; Microsoft Agent Framework's own "use a workflow for well-defined steps" guidance; 2026 post-mortems calling multi-agent frameworks overkill for cron-style dispatch). So: **built-in thin agent loop (default, OpenAI-compatible: works with OpenAI, Ollama, llama.cpp, LM Studio) + `pi` and `opencode` adapters** when installed.
- **Defer Qdrant/vector DB** (original doc itself wavered); SQLite memory tables suffice for MVP.
- **Web dashboard instead of TUI-first**: approvals/stop/live transcripts need an async UI (and it's what gets visually validated).

### Complaints → MVP design requirements (from documented incidents)
1. **Catch-up policy** for schedules missed while asleep (n8n "silent non-runs", cron misses) — coalesce missed runs + record event.
2. **DST/timezone correctness** — store UTC + IANA zone; croniter next-run math in bot's tz; per-bot single-instance lock (no double-fire/overlap).
3. **Append-only run transcripts + staleness view** — every run's events persisted (JSONL + SQLite); "last successful run" heartbeat per bot.
4. **Per-run & per-bot spend/step/time caps with hard kill** (Claude Code $447 silent bill; OpenCode infinite loops).
5. **Least-privilege workspaces** — path-jailed file ops; never ambient home-dir access (Grok uploaded a user's whole home dir; Muse read 6.8GB).
6. **Compound-command-aware policy engine** — parse `&&`, `||`, `;`, `|` before allow/deny matching (Claude Code allowlist bypass, unfixed for a year); denylist for `rm -rf /`, `curl|sh`, `sudo`, fork bombs.
7. **Approval presets + sticky "always allow"** per bot/tool so safe mode is bearable — users won't need yolo mode (top complaint across Claude Code/Codex).
8. **Egress guardrails** — deny piping secrets to network; browser tool isolated per-bot profile.
9. **Human-in-the-loop gates on irreversible actions** by default (OpenClaw shipped with none; Claude emailing real lawyers).
10. **Pause-to-human** on CAPTCHA/MFA/login walls with resumable runs + persistent browser profiles (Operator/browser-use session expiry complaints).

Not fixable at our scale (documented as out of scope): site bot-blocking, model hallucination, vendor rate-limit churn.

## 2. Scope

**In (MVP):** bot CRUD + templates; on-demand + cron-scheduled tasks; per-run isolated workspaces; built-in agent loop (mock/OpenAI-compatible providers) + pi/opencode adapters; tools: shell (jailed, policy-gated), files (path-jailed), memory (SQLite), browser (Playwright, optional, per-bot profiles, pause-to-human), web fetch; approvals queue; spend/step/time caps; append-only transcripts; FastAPI dashboard + REST API; Typer CLI; pytest suite (offline via mock runtime); marketing website; docs.

**Out:** multi-user, mobile, A2A collaboration, vector DB/RAG, containers, Windows/macOS polish (roadmap only).

## 3. Repo layout (new project at `~/CodingProjects/openbot`, git on `master`)

```
pyproject.toml  LICENSE(MIT)  README.md  CHANGELOG.md  .gitignore
src/openbot/
  config.py models.py store.py        # settings; Bot/Task/Run/Event/Approval models; SQLite store
  safety.py approvals.py              # compound-command classifier (deny/ask/allow), approval queue + sticky allows
  scheduler.py engine.py              # croniter+IANA tz+catch-up+locks; run lifecycle, caps, workers
  runtime/{base,builtin,mock,pi,opencode}.py
  tools/{base,shell,files,memory,browser,webfetch}.py
  server/{app.py, static/(index.html,app.js,style.css)}   # dashboard, vanilla JS, no build step
  cli.py templates.py demo.py         # Typer CLI; seed bot templates; demo seeding for screenshots
tests/   (safety, scheduler/tz, store, engine w/ mock runtime, API via TestClient)
docs/    (architecture.md, safety.md, bot-config.md, roadmap.md, research/orchestrators.md, research/complaints.md)
website/ (index.html, styles.css — static marketing site, no CDN dependencies)
```

Key designs: runs get `~/.local/state/openbot/bots/<bot>/<run_id>/workspace`; SQLite at `~/.local/state/openbot/openbot.db`; bot model spec like `mock/demo`, `openai/gpt-4o-mini`, `ollama/llama3.2` (+base_url); approval modes `ask_first_run` with sticky allows; global + per-bot concurrency (browser serialized by mutex); daemon = scheduler loop + worker pool + approval timeouts (default deny).

## 4. Build order (each step = one commit on master)

1. `chore: scaffold` — git init -b master, pyproject, LICENSE, .gitignore, README stub.
2. `feat(core): models + sqlite store` — migrations-lite schema, bot/task/run/event/approval CRUD.
3. `feat(safety): policy engine + approvals` — compound parser, deny/ask/allow rules, sticky approvals; unit tests.
4. `feat(tools): shell, files, memory, webfetch, browser` — path jail, timeouts, per-bot browser profiles; tests.
5. `feat(runtime): builtin loop + mock + pi/opencode adapters` — OpenAI-compatible tool-calling loop, step/token/time caps, event stream; mock provider for offline tests/demo; tests.
6. `feat(engine): orchestrator + scheduler` — queue, catch-up, tz-correct firing, per-bot locks, hard kill, transcripts; tests.
7. `feat(cli): typer CLI` — init/bot/run/runs/approvals/stop/status/daemon/serve/demo.
8. `feat(web): dashboard + api` — overview/bots/run-detail(live)/approvals views, stop/approve actions.
9. `feat(site): marketing website` — positioning "Your bots. Your machine. Your rules.", pain-points (cited complaints), features, vs Dots/Grok Bots/Muse comparison, safety story, quickstart, FAQ.
10. `docs: architecture, safety, bot-config, roadmap, research findings` — including the decision log (why own loop + adapters) and complaints→requirements table.
11. `test+fix: full suite green` — then visual validation pass (below) with fix commits.

## 5. Visual validation protocol

- `openbot demo seed` → mock-provider runs → dashboard screenshots (overview, run detail w/ live transcript, approvals, bot form) + marketing site (desktop 1440px + mobile 390px) via Playwright.
- Rendered PNGs go to `documents:visual-judge` agents (the single visual gate); every fail → fix → re-render → re-judge until pass.
- Full pytest run before final commit; README quickstart executed verbatim as a smoke test.

## 6. Environment notes

Python venv + pip (verify version at start); deps: typer, rich, pydantic, croniter, openai, fastapi, uvicorn, httpx; dev: pytest, pytest-asyncio; optional extra: playwright. No API keys needed anywhere in tests/demo (mock provider) — real models are opt-in via env vars.
